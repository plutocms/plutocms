Core owns the admin shell. A backend layer does not write it. The backend registers an **auth driver**, and core builds the shell from it.

## The shell

| Part | Route or place |
| --- | --- |
| Parent route | `/admin`. It redirects to `/admin/home`. |
| Sign-in page | `/admin/login` |
| No-access page | `/admin/no-access` |
| Route guard | A global route middleware for `/admin/**` |
| Navbar | The top bar with the user menu |
| Banners | Components that the admin layout shows above the page |

`/admin/**` has `ssr: false`. The admin is client-only. The server still checks every request. The guard only decides what the browser shows.

## The auth driver

A layer sets `authDriver` in `definePlutoExtension`. The last registered driver wins.

| Field | Purpose |
| --- | --- |
| `user()` | The signed-in user (`id`, `name`, `username`, `email`, `avatarUrl`), or `null`. |
| `loggedIn()` | Optional. The default is `user() !== null`. |
| `ready()` | A promise. It resolves after the first session check. It never rejects. |
| `refresh()` | Optional. Reads the session again. |
| `signOut()` | Ends the session. Core then shows a toast and goes to `/admin/login`. |
| `signIn` | The sign-in form component. Core passes it the `redirect` prop. |
| `signInTitle`, `signInDescription` | Text for the sign-in frame. Each is a key or a literal. |
| `links` | The `signUp` and `forgotPassword` URLs. |
| `publicPaths` | Paths that need no sign-in. |

`user` and `loggedIn` are getters, not refs. They read reactive state of the backend.

::warning
`loggedIn()` must give the same answer on the server and in the first client render. A backend with a cookie session that the server can read can answer on the server. A backend that learns the session in the browser answers `false` on the server. The navbar then appears after hydration.
::

## Other registry fields for the shell

| Field | Purpose |
| --- | --- |
| `accountMenu` | Items in the user menu. Sorted by `order`. |
| `adminBanners` | Banner components. The admin layout renders them. |
| `site` | `name()` and `url()` of the public site. |

A banner is a component with no props. It decides for itself if it shows.

## The route guard

The guard is `pluto-admin-auth.global.ts`. It works in this order:

1. With no auth driver, it does nothing.
2. It never touches a path outside `/admin`.
3. It waits for `driver.ready()`.
4. It calls `driver.guard(to)` when the driver has one. A returned local path is a redirect.
5. It decides with the public paths of the driver. A signed-out user on a private admin path goes to `/admin/login?redirect=<fullPath>`. A signed-in user on a public auth path goes to the `redirect` target, or to `/admin/home`.
6. For a signed-in user on a private path, it runs the staff step.

## The staff step

Only staff can enter the private admin pages. A staff user is a user with at least one capability. An admin holds `*`.

With no permissions driver, every signed-in user counts as staff.

A signed-in user with no capability goes to `/admin/no-access`. The page has three actions: **Try again**, **Go to the site**, and **Sign out**.

## Who sees the navbar

- On `/admin/**`, any signed-in user sees the bar. The exceptions are the public auth paths and a user who is known to be no staff.
- On a public page, only staff see the bar. A shop customer never sees it.

On a public page, the bar appears after the capabilities load. It is never in the first paint. If the load fails, the bar stays hidden.

An app that offsets its own header for the bar can use `usePlutoAdminBar().visible`.

## What the navbar has

In order:

1. The menu button, for small screens.
2. The logo and the site name.
3. **View site**, on `/admin/**` only.
4. The navbar actions.
5. The color mode button.
6. The user menu, when a driver is registered.

A `navbarActions` entry is a component action (`{ id, component }`) or a link action (`{ id, label, icon?, to, target? }`). A link action shows its label from the `lg` breakpoint. Below it, the label is the `aria-label`.

## The sign-in frame

`PlutoAdminAuthCard` is the frame of the sign-in page. It shows the logo, the site name, the heading, the `signIn` component, the footer links, and a **Back to the site** link.

A backend layer can use the same frame for its other auth pages. Give the card a default slot, and the slot replaces the form. Use the `title` and `description` props to replace the heading.

```vue
<PlutoAdminAuthCard title="supabase.auth.signup.title">
  <SignUpForm />
</PlutoAdminAuthCard>
```

## The tab title

On admin routes, `PlutoRoot` sets the title template to `Page - Site name`. Public routes keep the title template of the app.
