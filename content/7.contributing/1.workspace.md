Pluto is a set of repositories under the `plutocms` GitHub organization. Each project is its own git repository. A shared workspace folder holds them side by side.

| Repository | Package | Published |
| --- | --- | --- |
| `utils` | `@plutocms/utils` | Yes |
| `ui` | `@plutocms/ui` | Yes |
| `pluto` | `@plutocms/pluto` | Yes |
| `supabase` | `@plutocms/supabase` | Yes |
| `supabase-blog` | `@plutocms/supabase-blog` | Yes |

Stay inside the project that you work on. Do not change another project unless the task needs it.

## Commands

Every layer repository uses Bun. These scripts exist in most of them:

- `bun install` installs the dependencies. The `postinstall` hook runs `nuxt prepare`.
- `bun run dev` runs the layer as an app.
- `bun run lint`, `bun run typecheck`, `bun run test`, and `bun run build`. A repository defines only the scripts that it needs.

CI runs `lint`, `typecheck`, `test`, and `build`. Run them before you open a pull request. Do not run `typecheck` or `build` while the dev server runs, because both write to `.nuxt/`.

## Local layers

A layer reads an environment variable that points at a local checkout of an upstream layer. Use it to test a change before the upstream layer is released. When the variable is not set, the layer uses the published package.

| Variable | Layer |
| --- | --- |
| `PLUTO_UTILS_PATH` | `@plutocms/utils` |
| `PLUTO_UI_PATH` | `@plutocms/ui` |
| `PLUTO_PLUTO_PATH` | `@plutocms/pluto` |
| `PLUTO_SUPABASE_PATH` | `@plutocms/supabase` |
| `PLUTO_SUPABASE_STORAGE_PATH` | `@plutocms/supabase-storage` |
| `PLUTO_SUPABASE_BLOG_PATH` | `@plutocms/supabase-blog` |
| `PLUTO_SUPABASE_SHOP_PATH` | `@plutocms/supabase-shop` |
| `PLUTO_NUXT_CONTENT_PATH` | `@plutocms/nuxt-content` |

For example, `PLUTO_UTILS_PATH=../utils` makes a layer extend the local `utils` checkout. The docs site sets `PLUTO_NUXT_CONTENT_PATH` and `PLUTO_PLUTO_PATH` by itself in development, when the folders `../nuxt-content` and `../pluto` exist.

## The layer chain

Each layer extends the layers below it. An app extends only the top layer that it uses.

| Top layer | Also brings |
| --- | --- |
| `@plutocms/pluto` | `@plutocms/utils` |
| `@plutocms/nuxt-content` | `@plutocms/pluto` |
| `@plutocms/supabase` | `@plutocms/pluto`, `@plutocms/utils` |
| `@plutocms/supabase-shop` | `@plutocms/supabase`, `@plutocms/ui`, `@plutocms/utils` |
| `@plutocms/supabase-blog` | `@plutocms/supabase`, `@plutocms/supabase-storage`, `@plutocms/ui` |

See [Layers](/core/layers).

## Shared rules

### Feature documentation

Each project keeps a `FEATURES.md` at its repository root. It lists every implemented feature in one line each. Each feature has its full detail in a skill file at `.claude/skills/<feature-slug>/SKILL.md`. `FEATURES.md` links to each skill file.

When you add a feature:

1. Add one line to `FEATURES.md`.
2. Write the full detail in a new skill file.

### Writing style

All documentation, code comments, and commit messages use ASD-STE100 Simplified Technical English. See [Writing docs](/contributing/writing-docs).

### Git

- Use a semantic commit message for every commit. The format is `type(scope): summary`. Example: `feat(foo): bar baz`.
- Do not add a co-author line to a commit.
- Do not name a client site in the title or the body of a pull request. Describe the problem in general terms.
### Implementation plans

Every new implementation has a plan file. A session can end at any time, so the plan file keeps the context and the progress on disk.

- Put the file at `<project>/.claude/plan/<slug>.md`, in the project where the work happens. Work that changes more than one project goes in the workspace `.claude/plan/`.
- Write the file before you write code. A bug fix of one or two lines needs no plan file.
- Mark each checklist item done when it is done.
- Before you stop, write in the log where you stopped and what comes next.
- When the work is done, set `Status: done` and keep the file.

A plan file has these parts: a status line, the context (goal, reason, decisions, key files, open questions), a checklist, and a log.

### One Tailwind build

An app has exactly one Tailwind build. A layer never registers a `css` entry that imports `tailwindcss` or `@nuxt/ui`. A layer puts its tokens in `app/assets/css/pluto-layer.css`. See [Styles](/core/styles).

## Release order

The layers depend on each other. Release from the bottom up. See [Releasing](/contributing/releasing).
