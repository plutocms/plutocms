Pluto is a first-class part of a Nuxt app, but your site does not have to use Nuxt. The admin and the API of Pluto run in a Nuxt app. A site in any framework or language reads the published content from it.

You get two apps:

- **The Pluto app.** It has the admin at `/admin` and the API. Create it with `npm create pluto@latest`, and deploy it to a host with a server runtime. See [Deploy to Vercel](/guides/deploy-to-vercel).
- **Your site.** Any framework or stack. It reads the content in one of the ways below.

## Read the REST routes (GitHub mode)

The GitHub CMS has two public routes. They are anonymous, they return published items only, and they answer JSON.

```ts [Any JavaScript runtime]
const cms = 'https://cms.example.com'

// The published posts, without the body.
const list = await fetch(`${cms}/api/_pluto/cms/post?limit=10`).then(res => res.json())
// list = { data: [{ id, title, slug, excerpt, ... }], total, limit, offset }

// One post, with its body as sanitized HTML.
const post = await fetch(`${cms}/api/_pluto/cms/post/hello-world`).then(res => res.json())
// post = { id, title, slug, html, ... }
```

The routes, their options, and their cache headers are in [Public read](/github-cms/public-read#routes).

The routes send no CORS header. A server or a build step can call them from any origin. Browser code on another origin needs a CORS header on these routes. Add it in the `nuxt.config.ts` of the Pluto app, with the route rules of Nitro:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/api/_pluto/cms/post': { cors: true },
    '/api/_pluto/cms/post/**': { cors: true },
  },
})
```

Name each public type. Do not open `/api/_pluto/cms/**` as a whole, because the setup and build status routes are there too.

## Read the Markdown files (GitHub mode)

The content is Markdown with YAML frontmatter in your GitHub repository, for example `content/posts/hello-world.md`. A site that builds from that repository can read the files at build time, with any static site generator.

- Each save in the admin is a commit. The commit messages have a `[skip ci]` marker by default. Set `plutoCms.commit.skipDeploy: false` so that your host builds the site after each save. See [Commits](/github-cms/reference#commits).
- The frontmatter has a `status` key. Leave out the files with `status: draft`.

## Read Supabase (Supabase mode)

In Supabase mode, the content is in your Supabase project. Read it in either of these ways:

- **Supabase directly.** Use a Supabase client library, or the REST API of Supabase, with the anon key. Row level security gives an anonymous caller published rows only. See [Grants](/supabase/grants).
- **The routes of the layers.** For example, the [blog layer](/layers/blog#public-site) has `GET /api/post/list` and `GET /api/post/get/:id`, and the [shop layer](/layers/shop) has `GET /api/product/list` and `GET /api/product/get/:id`.

```ts [Any JavaScript runtime]
import { createClient } from '@supabase/supabase-js'

const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY)
const { data: posts } = await supabase.from('posts').select('*').order('created_at', { ascending: false })
```

## What stays in Nuxt

- The admin, the sign-in, and the extension points. A layer, a field widget, or a settings page is Vue and Nuxt code in the Pluto app.
- The composables, such as `usePlutoCmsList`, and the components, such as `PlutoMarkdown`. Your site uses the routes and renders the content with its own code.
- The admin bar with the **New** and **Edit** buttons shows only on the pages of the Pluto app.
