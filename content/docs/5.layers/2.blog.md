`@plutocms/supabase-blog` adds blog posts on top of the [Supabase layer](/docs/supabase). An admin can create, edit, list, and delete posts. A post has a title and a rich text body.

::pluto-figure{alt="The rich text editor of the blog layer" caption="A post in the rich text editor of the blog layer"}
::

## Install

The quickest start is the blog template with the Supabase backend:

```bash [Terminal]
npm create pluto@latest my-blog -t blog --backend supabase
```

The same template works with the Git CMS. See [CLI](/docs/reference/cli).

In an existing app, install the package first. `extends` does not install it.

:pluto-install{name="@plutocms/supabase-blog"}

Then extend only this layer:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@plutocms/supabase-blog']
})
```

The layer extends `@plutocms/supabase` (which extends `@plutocms/core`). Do not add them to `extends` and do not install them: the package manager installs them with the layer. You need the Supabase environment variables and the setup of the [Supabase layer](/docs/supabase). The images (the cover, and the images in the body) use the [media library](/docs/build/media) of core.

## The `posts` table

| Column | Meaning |
| --- | --- |
| `id` | bigint, primary key |
| `created_at` | Set by the database |
| `updated_at` | Set by the API on every create and edit |
| `slug` | Unique. It forms the public path `/posts/<slug>`, the same as the core blog. |
| `title` | Required |
| `content` | The body, in Markdown. It can hold inline images. |
| `cover` | Text. The id of a media record, or null. |
| `status` | `draft`, `review`, `scheduled`, or `published`. The default is `draft`. Migration `010_scheduled_publish.sql` adds `review` and `scheduled`. |
| `published_at` | Null until the first publish. The API sets it on the first publish only. For a scheduled post, it is the planned time. |
| `tag_ids`, `category_ids` | `bigint[]`, the ids of the tags and the categories of the post. Migration `007_post_terms.sql`. |
| `author_ids` | `bigint[]`, the ids of the authors of the post, in byline order. Migration `008_post_authors.sql`. |
| `seo_title`, `seo_description`, `seo_image`, `seo_noindex` | The SEO fields of the [SEO layer](/docs/layers/seo). Empty without that layer. Migration `006_post_seo.sql`. |
| `deleted_at` | The time the post went to the trash, else null. Migration `009_trash.sql`. |

A post that is unpublished and then published again keeps its first publish date.

## Capabilities

Row level security uses these capabilities, checked with `public.has_capability(cap)`:

| Capability | Allows |
| --- | --- |
| `posts:read_drafts` | Read a row that is not live (a draft, in review, or scheduled for later). An anonymous visitor reads only live rows: published, or scheduled with a time that has come. |
| `posts:write` | Insert a draft, edit a draft or a post in review, and send a post to review. It cannot publish, schedule, or change a published or scheduled post. Migration 010 gives it to every role that holds `posts:publish`. |
| `posts:publish` | Insert a row, update any row, publish, and schedule |
| `posts:delete` | Delete any row |
| `terms:manage` | Insert, update and delete a row of `tags` and `categories`. Migration 007 gives it to every role that holds `posts:publish`. |
| `authors:manage` | Insert, update and delete a row of `authors`. Migration 008 gives it to every role that holds `posts:publish`. |

An admin holds all six. There is no capability for ownership. A holder of `posts:publish` can edit every post.

Migration 010 adds the built-in role **Contributor** (`contributor`): `posts:write` and `posts:read_drafts`. A contributor writes posts and sends them to review. An editor with `posts:publish` publishes or schedules them. Give the role on the Users page.

## Trash

Migration `009_trash.sql` adds `deleted_at` to `posts`, `tags`, `categories`, and `authors`. A removed item goes to the trash for 30 days. A role with `posts:delete` moves a post to the trash. See [Trash](/docs/reference/content-model#trash).

## Tags and categories

Migration `007_post_terms.sql` adds the tables `tags` and `categories`, the two array columns of `posts`, and a trigger that removes a deleted term from the posts. A post save fails until the migration runs: apply it from `/admin/migrations`. The page [Tags and categories](/docs/build/tags-and-categories) describes the fields, the public API and the term pages.

## Authors

Migration `008_post_authors.sql` adds the table `authors`, the column `author_ids` of `posts`, and a trigger that removes a deleted author from the posts. Anyone reads the authors. A write needs `authors:manage`. A post save fails until the migration runs: apply it from `/admin/migrations`. The page [Authors](/docs/build/authors) describes the fields, the public API and the author pages.

## Admin views

| Route | Purpose |
| --- | --- |
| `/admin/posts` | List posts |
| `/admin/post/new` | Create a post |
| `/admin/post/edit/:id` | Edit a post |

These pages use the generic content UI of core with the `post` content type. The type uses the canvas layout and the post editor of core (`widget: 'post-canvas'` on the `content` field). See [The post editor](/docs/git-cms/editing#the-post-editor).

- The compose panel is next to a live preview of the site, in both modes.
- **Visual** mode shows the rich text editor of this layer, with the image upload.
- **Markdown** mode shows the Markdown source in a code editor with syntax colors.
- The left panel shows the outline of the post and the mode switch.
- The title and the slug are in the **Post** tab of the right panel.
- The toolbar shows the status (Draft, In review, Scheduled, or Published) and the save buttons. A user who can publish sees **Publish** and **Schedule**. A contributor sees **Submit for review**. See [Scheduled publish and review](/docs/reference/content-model#scheduled-publish-and-review).

See [Lists and forms](/docs/extend/forms).

## The rich text editor

The editor builds a Tiptap editor directly. It does not use the `UEditor` component of Nuxt UI. `UEditor` serializes the whole document to Markdown on every keystroke. Under fast typing, that work queues up and freezes the page.

The editor keeps the document as native ProseMirror state while the user types. It writes Markdown to the model only after a 400 ms pause, and on blur.

The editor has a fixed toolbar, a bubble toolbar, a suggestion menu, and a block menu in the drag handle. Mention, Emoji, Horizontal Rule, and Text Align are not in the editor.

- **Insert a component** in the toolbar, and the slash menu, add a component of the site. See [Components in posts](/docs/extend/author-components#components-in-posts).
- A URL alone on its line is an [embed](/docs/reference/content-model#embeds): the site shows the player.

### Images

The image button opens the media picker of core, with images only. The user picks a file or uploads one. The browser makes a photo WebP, at most 2400 px, with no location data. The editor then inserts the image into the body with its public URL.

The `cover` field is a `media` field with `accept: ['image/*']`. It stores the id of a media record in `posts.cover`. The public API gives the record in place of the id: `url`, `width`, `height` and `alt`. Show it with `PlutoImage`:

```vue
<PlutoImage :media="post.cover" sizes="xs:100vw lg:896px" class="h-auto w-full" />
```

## Public site

The public site reads posts through the [Public API](/docs/build/public-api). The `post` type is public.

- `GET /api/pluto/v1/content/post`. The published posts. A list item has no `content`. It has `excerpt`, the start of the body as plain text.
- `GET /api/pluto/v1/content/post/<id or slug>`. One published post. It has the stored `content` and `html`: the body rendered and sanitized, the same way as `PlutoProse`. A draft or a missing post gives 404.

In Nuxt, use `usePlutoPublicList('post')` and `usePlutoPublicItem('post', slug)`. A site in another stack calls the routes. Show `html` with the core component `PlutoHtml` (it works with every backend, so a page works with the Git CMS too), or with `PlutoProse` and `format="html"`.

```vue
<PlutoHtml :html="post.html" />
```

## `PlutoProse`

`PlutoProse` shows a stored rich text value (Markdown, HTML or Tiptap JSON) as sanitized HTML on a public page. It does not create a Tiptap instance. For the `html` of the public API, `PlutoHtml` of core is enough.

It has the class `pluto-prose`, as `PlutoHtml` has. For the look of the editor, import `@plutocms/css/base` in your CSS. See [Components](/docs/build/components#the-base-css).

```vue
<PlutoProse :content="post.html" format="html" />
```

| Prop | Default | Meaning |
| --- | --- | --- |
| `content` | none | The stored value |
| `format` | `'auto'` | `'auto'`, `'markdown'`, `'html'`, or `'json'` |
| `tag` | `'div'` | The wrapper element |
| `class` | none | Merged onto the wrapper, next to `pluto-prose` |

The slot `empty` shows when the result is empty.

### The pipeline

1. **Detect.** `detectRichtextFormat()` guesses if the value is Markdown, HTML, or Tiptap JSON.
2. **Convert.** `renderRichtext()` makes HTML. Markdown goes through `marked` with GFM. JSON goes through a small serializer. HTML passes through.
3. **Sanitize.** Every path ends with an allowlist sanitizer.
4. **Output.** The component sets the HTML as `innerHTML`.

`richtextToPlainText()` runs the same pipeline and strips the result to plain text. Use it for an excerpt or a meta description.

::warning
The format detection is a guess. Markdown that starts with a raw HTML block can be detected as HTML. Set the `format` prop when you know the format.
::

### Sanitizer rules

- Kept elements: `p`, `h1` to `h6`, `strong`, `b`, `em`, `i`, `s`, `del`, `u`, `code`, `pre`, `blockquote`, `ul`, `ol`, `li`, `hr`, `br`, `a`, `img`, tables, and checkbox `input`.
- Dropped with their children: `script`, `style`, `iframe`, `object`, `embed`, `svg`, `form`, `video`, and others of the same kind.
- Any other element is unwrapped.
- Every attribute is removed except a short list for each element. This removes `on*` handlers and `style`. A `p` keeps an empty `data-pluto-embed`.
- A `div` with the mark of a content component keeps its name and its safe props, and loses its children.
- `href` and `src` accept a relative path, `#anchor`, `?query`, `http:`, `https:`, `mailto:`, and a `data:image/*` URL for `png`, `jpeg`, `gif`, `webp`, and `avif`. `data:image/svg+xml` is never accepted.

### Limits

- Links get no automatic `target` or `rel`.
- Images get no automatic `loading="lazy"`.
- The JSON path understands only the nodes that the editor can produce. An unknown node renders as its children.

## Translation

The admin is translated to `en` and `pt-BR` in the `supabase-blog` namespace. `PlutoProse` has no UI text. The public site language belongs to your app. See [Internationalization](/docs/build/i18n).
