`@plutocms/docs` is a layer for sites that use [Nuxt Content](https://content.nuxt.com). Pluto edits the Markdown files. Nuxt Content reads the same files to build the public site.

This documentation site uses the layer. Its pages are Markdown files in a GitHub repository. Editors change them in the Pluto admin, with the Git CMS and no database.

## What the layer gives

- A `docs` page type. It maps the frontmatter of a Nuxt Content page to form fields.
- Nested, numbered folders. `content/1.getting-started/2.installation.md` is one item. The list shows the pages in tree order.
- A [visual block editor](/docs/guides/edit-pages-visually) for the body of a page, with a live preview. The editor does not need Markdown. A Markdown mode is one click away. Its **Insert** menu adds snippets: note, tip, code group, tabs, steps, cards, and more. Your own components join the palette with [`definePlutoBlock`](/docs/guides/author-components).
- A **View** link in the toolbar of the admin form. It shows in edit mode only, because a new page has no public route yet. It opens the page in a new tab.
- `usePlutoContentEditLink(page, type = 'doc')`: an "Edit in admin" link on the public page, for signed-in staff only. It gives `null` for everyone else. The link appears after hydration. It also tells the admin bar which page is on screen. It uses `usePlutoEditLink` of core.
- Admin bar buttons, for a user with `docs:write`. The `docs` type sets `adminBar: true`, so core draws them (see [New and Edit buttons](/docs/core/admin-shell#new-and-edit-buttons)):
  - **New** on every page where the admin bar shows. With one type, the button is **New Page** and opens `/admin/content/<type>/new`. With two or more types, one **New** button opens a menu. The docs types are in the `pages` group. When they are the only types, the menu lists them directly.
  - **Edit Page** on a public page that calls `usePlutoContentEditLink`. It opens the admin form of that page. It does not show in the admin, because the form has the **View** link.
- A CSS offset that keeps the Nuxt UI header and the sticky sidebar below the Pluto admin bar.
- English and Brazilian Portuguese text.

The layer extends `@plutocms/core`. Your app extends only `@plutocms/docs`. Do not add `@plutocms/core` to `extends`.

## The docs page type

The `docs` preset makes one content type for the pages of a Nuxt Content site.

- Items are nested Markdown files. The id is the path under `source`, without `.md`, such as `2.core/03.content-model`.
- A page has no draft state and no stored dates: `status` and `timestamps` are off.
- The list sorts by id in tree order: `index` first, then the numeric prefixes as numbers.
- The capabilities are `docs:write` and `docs:delete`. There is no read capability.
- The form uses the canvas layout: the body fills the page, and the other fields are in the **Page** tab of the right panel.

| Field | Frontmatter key | Region |
| --- | --- | --- |
| Title (required) | `title` | Page tab |
| Slug (required). It holds the whole path. | None. It is the file path. | Page tab |
| Description | `description` | Page tab |
| Body. The visual editor, with `widget: 'mdc'`. | None. It is the file body. | Canvas |
| Navigation title | `navigation.title` | Page tab |
| Navigation icon | `navigation.icon` | Page tab |
| Hidden in navigation | `navigation: false` | Page tab |
| SEO title | `seo.title` | Page tab |
| SEO description | `seo.description` | Page tab |

A save writes the flat fields back into `navigation` and `seo`. Other keys stay as the author wrote them, for example `navigation.badge`, `seo.ogImage`, and `links`. A hidden page writes `navigation: false`, which replaces its navigation title and icon. A save that changes nothing makes no commit.

## Requirements

- Node 22.5 or newer. The layer sets the native SQLite connector of Nuxt Content.

## Installation

::steps
### Install the package

`extends` does not install an npm package. Install it first.

:pluto-install{name="@plutocms/docs"}

### Add the layer

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@plutocms/docs'],

  plutoDocs: {
    types: [{ preset: 'docs', name: 'doc', source: '' }],
  },
})
```

The layer sets `plutoGithub.postType: false` and `plutoGithub.commit.skipDeploy: false`. The other `plutoGithub` options use the Pluto defaults: the CMS is on, the storage is `fs` in development and `github` in production, and Pluto finds the repository from `PLUTO_GITHUB_REPO`, from Vercel, or (in development) from the git remote. See [Reference](/docs/git-cms/reference#defaults).

### Define the collections

Define the collections in `content.config.ts`, as for any Nuxt Content site. The layer defines no collection.

### Start the CSS entry

```css [app/assets/css/main.css]
@import 'tailwindcss';
@import '@nuxt/ui';
@import '#build/pluto.css';
```

### Use PlutoRoot

Use `PlutoRoot` in `app.vue` instead of `UApp`. Render the admin routes (`/admin/**`) and the preview route (`/_pluto/preview`) with only `<NuxtPage />`. Render the public routes with your own header, main and footer. See [Edit pages visually](/docs/guides/edit-pages-visually#add-the-preview-to-your-site). `PlutoRoot` renders a `NuxtLayout`, so do not use a page layout for the docs sidebar. Put the sidebar in a component.

### Offset the site header

Give the class `pluto-header-offset` to the `UHeader` of the site. The layer then keeps the header, the page aside, and the table of contents under the admin bar. The variable `--pluto-site-header-height` is the height of your header. The default is `4rem`. See [Offset your header for the admin bar](/docs/git-cms/public-read#offset-your-header-for-the-admin-bar).

### Create the GitHub App

Deploy the site, open `/admin/login`, and select **Create the GitHub App**. See [Quickstart](/docs/git-cms/quickstart). To create the App by hand, see [GitHub App](/docs/git-cms/github-app).
::

## Options

`plutoDocs.types` is a list. Each entry has these options:

| Option        | Description                                                                  |
| ------------- | ---------------------------------------------------------------------------- |
| `preset`      | The preset. Only `docs` exists.                                              |
| `name`        | The content type name. The admin URL is `/admin/content/<name>`.             |
| `source`      | The folder under the CMS content dir. Use `''` for the content dir itself.   |
| `label`       | The singular label. The default is `Page`.                                   |
| `labelPlural` | The plural label. The default is `Pages`.                                    |
| `exclude`     | Ids to hide: an id (`index`), or a folder with a trailing slash (`drafts/`). |
| `routePrefix` | The route prefix of the pages on the public site. The default is none.       |
| `navGroup`    | The nav group of the type. The default is `'pages'`. Use `false` for no group. |
| `icon`        | The icon of the type in the admin. The default is `lucide:book-open`.          |

- `name` uses lowercase letters, numbers, and dashes. It starts with a letter. It is unique.
- `source` is `''` or a nested folder path, such as `1.docs/api`.
- The types are in the `pages` group of core by default. In the admin sidebar they show as the children of one **Pages** item. `navGroup: false` gives a type its own item.
- A type with a problem is dropped, and the module logs one error for it.

`plutoDocs` has more options: `render`, `runtimeMaxAge`, and `blocks.discover` (`false` turns off the discovery of block components). `render` is `'hybrid'` (default), `'build'` or `'runtime'`. See [Build time, run time or both](#build-time-run-time-or-both).

The layer is off, with an error in the log, when the app sets `plutoGithub.enabled: false`.

To test an unpublished checkout, use the `plutoLayer` helper. It reads `PLUTO_LOCAL_ROOT`. The docs site does this:

```ts [nuxt.config.ts]
import { plutoLayer } from '@plutocms/core/layers'

export default defineNuxtConfig({
  extends: [plutoLayer('@plutocms/docs')]
})
```

See [Local layers](/docs/contributing/workspace#local-layers).

::note
The layer sets `plutoGithub.commit.skipDeploy` to `false`. In `'build'` mode, Nuxt Content builds the content at build time, so each edit must start a new deploy. In `'hybrid'` and `'runtime'` mode, the server reads the new text, so the page shows before the deploy ends. The deploy still keeps the build data current.
::

## Build time, run time or both

`plutoDocs.render` sets how the public pages get their content. It has three values. The default is `'hybrid'`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  plutoDocs: {
    types: [{ preset: 'docs', name: 'doc', source: '' }],
    render: 'hybrid' // or 'build', or 'runtime'
  }
})
```

::note
`'hybrid'` is the default. Before this option, the layer behaved like `'build'`. Set `render: 'build'` to keep that behavior.
::

::tabs
  :::tabs-item{label="Hybrid" icon="i-lucide-split"}
  This is the default. Nuxt Content builds the pages when the site builds, as in build mode. At run time, the server compares the files in the content repository with the files of the build. While nothing differs, the pages come from the build data, with no GitHub read for the pages.

  - A page that changed after the build comes from the repository, so a save shows on the next request. A new page comes from the repository too.
  - When any file differs, the navigation and the previous and next links come from the repository. A new page is in them at once.
  - A page that was removed gives a 404, and it leaves the navigation.
  - When the next deploy is live, its build matches the repository again, so all the pages come from the build data.
  - When the repository cannot be read (no GitHub App, a rate limit, an outage), the build data answers. The site does not go down because of GitHub.
  - It needs a server (Node, or a serverless host). A fully static host cannot use it.
  :::

  :::tabs-item{label="Build time" icon="i-lucide-hammer"}
  Nuxt Content builds the pages when the site builds. A save is a commit, and the commit starts a new build. The site can be fully static.

  - Fast pages. The host serves ready files, and no page needs a GitHub call.
  - Works on any static host, with no server.
  - A save shows after the build ends. A new page also shows in the navigation after that build.
  :::

  :::tabs-item{label="Run time" icon="i-lucide-zap"}
  The server reads the Markdown from the content repository when a visitor asks for a page. It uses the [Git CMS](/docs/git-cms) store and its cache. It parses the text on the server, with the same parser as Nuxt Content, and renders it with the same components.

  - A save shows on the next request, with no build. The navigation and the previous and next links come from the repository tree, so a new page shows in them at once.
  - It needs a server. A fully static host cannot use it.
  - Every page costs GitHub reads. The cache keeps them low, but without a fresh cache a request waits for GitHub, and a GitHub error is an error for the visitor.
  :::
::

### How hybrid mode compares the files

At build time, the module writes a manifest: for each content type, the path of each `.md` file and its version. The version is the same value that the content store reports for the file (`_version`). For the GitHub store it is the Git blob id. A file with Windows line endings (CRLF) is hashed with LF for GitHub, because Git keeps LF in the repository. For the local file store (development), the file is hashed as it is on the disk.

The manifest is a virtual module of the server bundle. The server reads it at run time. On a request, the server lists the files of the type through the [Git CMS](/docs/git-cms) store. The store caches this list by the head of the branch, so it costs at most one GitHub call in `plutoGithub.cache.headTtl` seconds. The server then compares the list with the manifest.

The manifest covers `.md` files. A change of a `.navigation.yml` file shows after the next deploy, unless a page also changed. Then the server reads the `.navigation.yml` files from the repository with the navigation.

### What to know before you choose

- **No prerender of the content pages.** In hybrid and run-time mode, do not prerender the pages: a prerendered page is a file, and it hides a later edit. Remove `crawlLinks` and the prerender routes of the pages. A route that is not a content page can stay prerendered. If you use `nuxt-og-image` with `zeroRuntime`, turn it off: the images then render at run time.
- **The search stays build time.** It reads the index that Nuxt Content builds, so a new or changed page is in the search after the next build.
- **GitHub reads.** In hybrid mode, the reads happen for the list of files, and for a page that changed. In run-time mode, they happen for every page. A save clears the head cache of the server that took the save. Other server instances show a change within `cache.headTtl` seconds, so use a short value, for example `plutoGithub.cache.headTtl: 5`.
- **A short public cache.** The layer routes answer with a `Cache-Control` header of 10 seconds by default. Set `plutoDocs.runtimeMaxAge` (seconds) to change it. `0` turns the cache off.
- **The edit form shows "Live" at once.** The layer sets `liveOnSave` on its content types in hybrid and run-time mode. The form then does not wait for the build.
- **The admin and the editor do not change.**

### Pages that work in every mode

A page does not call `queryCollection` for the content. It uses three composables of the layer. They give the same data in every mode, so a change of `render` needs no change in the pages.

| Composable | Description |
| --- | --- |
| `usePlutoContentPage(path, { collection })` | The page at a route path, or `null`. Pass it to `ContentRenderer`. |
| `usePlutoContentNavigation({ collection })` | The navigation tree. Pass it to `UContentNavigation`. |
| `usePlutoContentSurround(path, { collection })` | `[previous, next]`, each an item or `null`. Pass it to `UContentSurround`. |

Each one returns the result of `useAsyncData`. `collection` is the Nuxt Content collection that `'build'` and `'hybrid'` mode query. `'runtime'` mode ignores it and reads the content type (the first type, or the `type` option). In `'hybrid'` and `'runtime'` mode, the composables call the routes `/api/pluto/v1/docs/:type/{page,navigation,surround}`. They are on the [Public API](/docs/core/public-api): the answer is `{ data }`, and a site in another stack can call them too, with the `path` and `collection` query keys.

The docs type is public on the content API of core as well: `/api/pluto/v1/content/<type>` lists the pages, and `/api/pluto/v1/content/<type>/<id>` gives one page with `html`. That `html` comes from plain Markdown: the MDC syntax goes and its text stays. A headless docs site that renders the components uses the `page` route, which gives the parsed body.

```vue [app/pages/[...slug].vue]
<script setup lang="ts">
const route = useRoute()
const { data: page } = await usePlutoContentPage(() => route.path, { collection: 'docs' })
const { data: surround } = await usePlutoContentSurround(() => route.path, { collection: 'docs' })
</script>
```

### What a page read from the repository has

- The `.navigation.yml` file of each folder: the title, the icon and the other keys, and `navigation: false` to hide a folder, as Nuxt Content applies them.
- All the frontmatter of the file. The keys that are not page fields (for example a custom `links` list) are at the top level of the page and in `page.meta`. Nuxt Content puts the keys that the collection schema declares at the top level and the other keys in `meta`. The layer does not know the schema, so it sets both.
- The root `index` page is the landing page. The navigation built from the repository leaves it out. Use `usePlutoContentNavigation({ includeRoot: true })` to keep it.
