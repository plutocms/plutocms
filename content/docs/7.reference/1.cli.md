The `create-pluto` command makes a new project from a template (or from scratch), installs the dependencies, and tells you how to start it. For the default setup, see the [Quickstart](/docs/start-here/quickstart): press Enter at each question.

## Run the CLI

::code-group{sync="package-manager"}
```bash [npm]
npm create pluto@latest
```

```bash [pnpm]
pnpm create pluto@latest
```

```bash [yarn]
yarn create pluto
```

```bash [bun]
bun create pluto@latest
```

```bash [deno]
deno run -A npm:create-pluto@latest
```
::

## The wizard

The wizard asks these things, in this order:

1. **Project directory.** The default is `my-pluto-project`. The CLI makes the directory if it does not exist.
2. **Website title.** The default is `My Awesome Website`.
3. **Backend.** Choose `Git CMS (Markdown files in Git)` or `Supabase`. With the Git CMS, the CLI also makes the project a Git repository: in development, each save in the admin is a commit in it.
4. **Supabase values.** Only for Supabase. See [With Supabase](#with-supabase).
5. **Template.** The list shows the starter templates that the backend allows, then **Start from scratch**.
6. **Layers.** Only for `Dashboard only` and **Start from scratch**. See [Dashboard only](#dashboard-only).
7. **Package manager.** `npm`, `pnpm`, `yarn`, `bun` or `deno`. The default is the one that runs the CLI.

| Template | `-t` | Backends |
| --- | --- | --- |
| Blog (minimalist) | `blog` | Git CMS, Supabase |
| Shop (Supabase) | `supabase-shop` | Supabase |
| Dashboard only | `dashboard` | Git CMS, Supabase |
| Start from scratch | `none` | Git CMS, Supabase |

The templates are in the [templates repository](https://github.com/plutocms/templates). The CLI reads its list of templates, so a new template does not need a new version of the CLI.

### Start from scratch

The CLI downloads nothing. It writes a Nuxt app that extends Pluto, with no pages of its own: `package.json`, `nuxt.config.ts`, `app/app.vue`, `tsconfig.json`, and `.gitignore`. It is a good start for an agent, or for a site that you write yourself. It works with both backends, and it can add layers, as [Dashboard only](#dashboard-only) does.

### Dashboard only

This template has no public site. It is Pluto with the admin at `/admin` and the [public API](/docs/build/public-api): a headless CMS to deploy, for a site in any stack. The home page redirects to `/admin`. See [Use Pluto headless](/docs/build/use-pluto-headless).

It works with both backends. The CLI sets the backend in it. With Supabase, the layer in `nuxt.config.ts` becomes `@plutocms/supabase`. Then the wizard asks which layers to add. You can select several:

| Backend | Layers |
| --- | --- |
| Supabase | `Shop`, `Blog`, `3D` |
| Git CMS (Markdown files in Git) | `3D` |

The CLI adds each layer to `extends` in `nuxt.config.ts` and to `package.json`. `Shop` and `Blog` extend `@plutocms/supabase` themselves, so the app extends them in place of `@plutocms/supabase`. See [Layers](/docs/extend/layers).

The blog is one template for both backends. The pages are the same. The CLI sets the backend in it: the layer in `nuxt.config.ts` (`@plutocms/core` or `@plutocms/supabase-blog`), the packages, the sample posts in `content/` (Git CMS only), and the `.env`.

Then the CLI downloads the template, writes `.env`, and installs the dependencies. The `name` in `package.json` becomes the name of the project directory. At the end, it shows the next steps:

```text [Terminal]
◇  Next steps
│  cd my-pluto-project
│  npm run dev
│
│  Then open /admin on the dev server.
│
│  Local Git publishing works in development only. To publish from a
│  deployed site, connect GitHub (Settings > GitHub).
└  Docs: https://pluto.vulmix.dev/docs/start-here/quickstart
```

The note about local Git shows only for the Git CMS. The dev command follows the package manager: `pnpm run dev`, `bun run dev`, `deno task dev`, and so on.

Before the download, the wizard checks two things. If `nuxt.config.ts` exists in the current directory, the wizard asks "Nuxt project detected. Do you want to add Pluto environment variables?". If the target directory is not empty, the wizard asks for confirmation.

You can cancel at any prompt.

## Skip the prompts

| Option | What it does |
| --- | --- |
| `<folder>` (first argument) | The project directory. |
| `-t`, `--template` | The id of a template: `blog`, `supabase-shop`, `dashboard`, or another free template of the [templates repository](https://github.com/plutocms/templates). `none` starts from scratch. It skips the template prompt. |
| `--backend` | `git` (the Git CMS) or `supabase`. It skips the backend prompt. |
| `--layers` | The layers to add to `dashboard` or `none`, separated by commas: `shop`, `blog`, `3d`. `none` adds no layers. It skips the layers prompt. |
| `--pm`, `--package-manager` | The package manager. It skips that prompt. |
| `--no-install` | Do not install the dependencies. The next steps then show the install command. |

```bash [Terminal]
npm create pluto@latest my-blog -t blog --backend git --pm pnpm
npm create pluto@latest my-cms -t dashboard --backend supabase --layers shop,3d
npm create pluto@latest my-app -t none --backend git
```

The Supabase shop works with Supabase only, so `-t supabase-shop` needs no `--backend`. The blog asks for the backend when `--backend` is not set. A template with a backend that it does not support (`-t supabase-shop --backend git`), an unknown name, or an unknown package manager stops the CLI: it prints the right names and exits with status 1.

In a script (no terminal), the CLI does not ask for the website title, the layers or the package manager. It uses the defaults, and adds no layers. So `create-pluto my-blog -t blog --backend git --pm bun` runs with no question.

## What the CLI writes

The CLI downloads the folder of the template from GitHub with `giget`, for example `gh:plutocms/templates/templates/blog`. The project gets that folder only: no workflow and no other file of the templates repository.

The CLI reads the list of templates from `templates.json` of the [templates repository](https://github.com/plutocms/templates). Set `PLUTO_TEMPLATES_URL` to read another list (a URL or a local file). When the list does not load, the wizard offers **Start from scratch** only.

Then it writes a `.env` file. If `.env` exists, the CLI merges the new values into it. Each value is quoted.

The CLI always writes the website title as `NUXT_PUBLIC_WEBSITE_NAME`.

### With Supabase

The CLI asks for three values. It checks each one.

| Prompt | Variable |
| --- | --- |
| Supabase URL | `SUPABASE_URL` |
| Supabase key | `SUPABASE_KEY` |
| Database connection string (`postgres://` or `postgresql://`) | `DATABASE_URL` |

You need a Supabase project first. You can make one at [database.new](https://database.new/). Find the connection string in the Supabase dashboard: Project Settings, Database, Connection string. The pooler connection string also works.

### With the Git CMS

The CLI asks nothing about GitHub. It writes `NUXT_PLUTO_GITHUB_SESSION_PASSWORD`, a random value with 43 characters.

You make the GitHub App later, from the admin of your site:

- **On your machine,** you need no App. The dev server signs you in as a local user and edits the files in `content/`.
- **After a deploy,** open `/admin/login` and select **Create the GitHub App**. See [Deploy](/docs/start-here/deploy).

## Local layers

A normal project uses the npm packages and needs no setup for local layers. The `plutoLayer` helper and `PLUTO_LOCAL_ROOT` are for people who work on Pluto itself. See [Local layers](/docs/contributing/workspace#local-layers).
