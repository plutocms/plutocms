All documentation, code comments, and commit messages in Pluto use **ASD-STE100 Simplified Technical English**.

## The style

- Use short sentences.
- Put one instruction in each sentence.
- Use active voice.
- Use simple, consistent words. Use the same word for the same thing.

| Do | Do not |
| --- | --- |
| Run `bun install`. | The dependencies should be installed by running `bun install`. |
| The route returns 404. | A 404 is what the route will return in this case. |
| Core shows a skeleton while the chunk loads. | A skeleton is shown by core during the loading of the chunk. |

## Document only what the source says

Before you write a page, read its source: the code, the skill files of the project, and the `FEATURES.md` file. A README can be out of date, so check it against the code. When the code and a skill file disagree, trust the code. Do not invent an option, a route, or a behavior. If a source is unclear, leave the detail out.

Do not name a client site in the docs.

## Update the docs with every change

A change is not done until its docs are up to date. In the same pull request as the code, update:

- The pages of this site that describe the behavior, the options, the commands, or the setup steps that changed. Add a page when a feature has none.
- The skill file and the `FEATURES.md` line of each project that changed.
- The README, when the change touches what it shows. A README stays short: what the project is, how to install it, and a link to these docs.

## Pages are Markdown files

The pages are Markdown files in the `content/` folder of the docs repository. Nuxt Content reads them.

- Prefix a file or a folder with a number to set its order: `1.start-here`, `2.quickstart.md`.
- Use a leading zero when a folder has 10 or more pages: `01.layers.md`, `10.mail.md`.
- Put a `.navigation.yml` file in each folder with a `title` and an `icon`.

```yaml [content/docs/1.start-here/.navigation.yml]
title: Start here
icon: i-lucide-rocket
```

## Frontmatter

Each page has a `title` and a `description`. Add a `navigation.icon` with a Lucide icon where it fits.

```md [content/docs/6.extend/02.layers.md]
---
title: How layers work
description: Learn how the core layer and other layers work together.
navigation:
  icon: i-lucide-layers
---
```

## MDC components

Use these components where they help:

| Component | Use |
| --- | --- |
| `::note` | Extra information |
| `::tip` | A useful hint |
| `::warning` | A risk the reader must know |
| `::caution` | A danger, such as data loss |
| `::code-group` | Code for several package managers |
| `::steps` | Numbered steps with headings |
| `::card-group` | Links to other pages |
| `::field-group` | A group of fields |
| `::pluto-screenshot` | A screenshot of the admin or a site |

```md
::warning
Do not put a secret in the build environment.
::
```

Give a code block a file name or a label in square brackets:

````md
```ts [nuxt.config.ts]
export default defineNuxtConfig({})
```
````

Wrap placeholders such as `<label>` in backticks. A bare angle bracket in prose is parsed as HTML.

## Where a page goes

Put a page in the section of its reader:

- **Start here**: the default path only. No options and no choices.
- **Build your site**: the tasks of a person who builds a site with Pluto.
- **Git CMS**, **Supabase**, **Layers**: the details of one backend or one layer.
- **Extend Pluto**: the admin from the inside, for people who write layers. It is optional.
- **Reference**: every option, for a reader who looks something up.

Start each page with what works with the defaults. Put options and edge cases after it.

## Screenshots

```md
::pluto-screenshot{name="media-library" alt="The media library in the admin" hint="The Media page with a grid of images"}
::
```

- The image is `app/assets/screenshots/<name>.png` (`.webp` and `.jpg` also work). Add the file: the page shows it at the next build, with no change in the Markdown.
- Until the file exists, the page shows a dashed placeholder with the `hint` and the file path.
- Add `<name>.dark.png` for the dark mode. Without it, the light image shows in both modes.
- Capture at 1440 × 900, with the browser zoom at 100%. Crop out the browser frame.
- `alt` describes the image for a screen reader. `hint` is the caption.

## Edit pages in the admin

This site extends the `@plutocms/docs` layer. The layer lets editors change these files in the Pluto admin at `/admin`. See [Docs](/docs/layers/docs).

- In development, the admin reads and writes the local `content/` folder. You are signed in as a local user.
- In production, the admin reads and writes the GitHub repository. Each save is a commit, and the commit message has no `[skip ci]` marker, so the site redeploys.
- The site uses the hybrid render mode. A saved page shows on the site at once, before the new build is live. See [Build time, run time, or both](/docs/layers/docs#build-time-run-time-or-both).
- The site uses the npm packages. Set `PLUTO_LOCAL_ROOT=..` in `.env` to use your local `../pluto` checkout (core and the docs layer). `PLUTO_USE_LOCAL=false` turns it off again. See [Workspace](/docs/contributing/workspace).

The admin edit form has fields for the title, the description, the navigation, and the SEO values. They map to the `title`, `description`, `navigation`, and `seo` keys of the frontmatter.

## Check your work

Run the dev server and open your page. Run the lint and the build before you open a pull request. In hybrid mode, the build does not prerender the docs pages, so it does not find broken links. Open the pages that you changed and check their links.

```bash [Terminal]
bun run dev
bun run lint
bun run build
```
