A post can have tags and categories. This works on both backends (the Git CMS and Supabase), on a server and on a static site. Readers get a page for each term: `/tags/<slug>` and `/categories/<slug>`.

Pluto has no taxonomy system. A **term** is a content type. A post stores the ids of its terms in a `reference` field with `multiple`. The term pages are the [public API](/docs/build/public-api) with a filter.

The [blog template](https://github.com/plutocms/templates/tree/main/templates/blog) has the term pages already.

## The terms

Each backend registers two content types, `tag` and `category`. A term has a `title` (shown as **Name**), a `slug` and a `description`. Categories are flat: a category has no parent.

| | Git CMS | Supabase |
| --- | --- | --- |
| Where a term lives | `content/tags/<slug>.md` and `content/categories/<slug>.md` | The tables `tags` and `categories` |
| Where a post keeps its terms | A YAML list of slugs in the front matter | The columns `tag_ids` and `category_ids` (`bigint[]`) |
| Id of a term | The slug (the file name) | The number id of the row |
| Set up | Nothing. The types register with `postType`. | Run the migration `007_post_terms.sql` of [`@plutocms/supabase-blog`](/docs/layers/blog) |

### Git CMS

A term is a Markdown file with a `title`. A post lists the slugs of its terms:

```md [content/tags/hiking.md]
---
title: Hiking
---
```

```yaml [content/posts/a-weekend-in-the-hills.md]
---
title: A weekend in the hills
categories:
  - travel
tags:
  - hiking
  - winter
---
```

- The types register when `plutoGithub.postType` is on, which is the default. With `postType: false`, the types are not there.
- A post with a slug that has no term file shows no tag for that slug in the public API.
- An empty list removes the key from the front matter.
- A **rename** of a term (a new slug) or a **delete** rewrites the posts that use it, drafts too. The change is in the same commit as the term change, for example `content(tag): rename "a" -> "b" (3 references)`. If a post changes while the commit runs, the save answers 409.

### Supabase

Migration `007_post_terms.sql` of `@plutocms/supabase-blog` adds:

- the tables `tags` and `categories`, with the policies and the grants;
- the columns `tag_ids` and `category_ids` on `posts`, with a GIN index each;
- a trigger on each term table. When you delete a term, the trigger removes its id from every post.

The posts keep the ids in an array column, so the database has no foreign key for each id. The trigger keeps the arrays clean. Apply the migration from `/admin/migrations` before you save a post. See [Migrations](/docs/supabase/migrations).

## Who can manage terms

Creating, editing and deleting a term need the `terms:manage` capability.

- **Git CMS:** a user with push access gets it with the other capabilities of the registered types.
- **Supabase:** migration 007 gives `terms:manage` to every role that holds `posts:publish`. An admin holds all capabilities.

A user without `terms:manage` can still pick the existing terms in a post.

## The post form

The side panel of the post form has two fields, **Categories** and **Tags**. Each one is a multi-select with a search box. A selected term is a chip.

To add a term that does not exist, type its name and select **Create "…"**. Pluto creates the term with the name and a slug made from it, then selects it. The option shows only for a user with `terms:manage`. If a term with the same name or slug exists, Pluto selects it and creates nothing.

The post list shows the categories of each post as badges.

## Read terms in the public API

The terms are public content types, so they have their own routes: `/api/pluto/v1/content/tag` and `/api/pluto/v1/content/category`.

A post answer has its terms in place of the ids. Each term is `{ id, label, slug }`:

```json
{
  "id": "a-weekend-in-the-hills",
  "title": "A weekend in the hills",
  "categories": [{ "id": "travel", "label": "Travel", "slug": "travel" }],
  "tags": [{ "id": "hiking", "label": "Hiking", "slug": "hiking" }]
}
```

- A post with no term has `[]`.
- A term that is not there anymore is not in the answer.
- Core reads the terms one time for all the posts of an answer.

To list the posts of a term, filter by the slug or by the id:

```bash [Terminal]
curl "https://your-site.dev/api/pluto/v1/content/post?filter[tags]=hiking"
```

A slug or an id that matches no term gives an empty list. The filter works on a static site too. See [Public API](/docs/build/public-api#query).

## Term pages in a Nuxt site

Four composables read the terms: `useTags`, `useTag`, `useCategories` and `useCategory`. They sort by title. A post of `usePosts` has `tags` and `categories`.

```vue [app/pages/tags/[slug].vue]
<script setup lang="ts">
const route = useRoute()
const { tag } = await useTag(() => String(route.params.slug))
const { posts } = await usePosts({
  filter: { tags: String(route.params.slug) }
})
</script>

<template>
  <h1>{{ tag?.title }}</h1>
  <PostList :posts="posts" />
</template>
```

The blog template has these pages:

| Page | Content |
| --- | --- |
| `/tags` | Every tag. |
| `/tags/<slug>` | A tag and its posts, with search and pages. |
| `/categories/<slug>` | A category and its posts, with search and pages. |
| `/` | The home page has a bar of category links. |

A post page shows its categories above the title and its tags after the text.

### Static sites

The build finds a page when a link points to it. So link every term: the home page links the categories, and `/tags` links every tag. A term with no link has no page in the build.

### The preview link

A term has a **View** link in the admin. Its `previewUrl` is `/tags/<slug>` or `/categories/<slug>`. If your site uses other paths, change it with `extendContentTypes`. See [Extend a content type of another layer](/docs/reference/content-model#extend-a-content-type-of-another-layer).

```ts [shared/utils/term-paths.ts]
export const termPathsExtension: PlutoContentTypeExtension = {
  id: 'term-paths',
  extend: type =>
    type.name === 'tag'
      ? { ...type, previewUrl: item => (item.slug ? `/topics/${item.slug}` : undefined) }
      : type
}
```

Register it on the client with `definePlutoExtension` and on the server with `extendContentTypes`, as in the guide above.

## Terms on your own content type

Any content type can reference another one. Add a `reference` field with `target`:

```ts
{
  name: 'genres',
  type: 'reference',
  label: 'Genres',
  target: 'genre',
  multiple: true,
  create: true,
  region: 'side',
  inList: true
}
```

- `target` is the name of the other content type. The field stores the id of an item of that type.
- `multiple` stores a list of ids, in order. Without it, the field stores one id.
- `create` lets the widget create an item of `target` from the field. It needs `target`, and the user needs the write capability of the target.

If `target` is a public type, the public API gives `{ id, label, slug }` in place of each id. If it is a private type, the API keeps the ids. On Supabase, a `multiple` field needs an array column such as `bigint[]`, and the adapter filters it with `.contains`. See [Content adapter](/docs/supabase/content-adapter).

## Limits

- Categories are flat. There is no parent category.
- The post form loads up to 1000 terms of a type. A blog with more terms needs a server search, which Pluto does not have yet.
- On the Git CMS, a rename reads every file of each type that references the term. On a large blog, one commit writes many files.
- On GitHub, an inline create is its own commit and its own build. The next save can cancel the build before it ends.
- A term has no SEO fields.
