On a live site, the posts stay in your GitHub repository. Editors sign in with GitHub, and each save is a commit on GitHub. You do not fill in any GitHub settings by hand: Pluto sends them to GitHub, and GitHub creates the App after you confirm.

You need:

- The project from the [Quickstart](/docs/start-here/quickstart), pushed to a GitHub repository.
- A host with a server runtime. This page uses [Vercel](https://vercel.com/). A static export does not work: the admin and the content routes run on the server.

::steps{level="2"}

## Deploy the site

In Vercel, import the GitHub repository and deploy. Vercel detects Nuxt. You set no environment variable now: the site builds and runs without the GitHub App.

::pluto-screenshot{name="deploy-vercel-import" alt="The Vercel page that imports a GitHub repository" hint="Vercel: Import Git Repository, with the Pluto project selected"}
::

## Create the GitHub App

Open `https://<your-site>/admin/login`. The page shows the checklist **Set up the GitHub sign-in**. Select **Create the GitHub App**.

::pluto-screenshot{name="deploy-github-checklist" alt="The sign-in page with the GitHub setup checklist" hint="/admin/login on the live site, with the Set up the GitHub sign-in checklist"}
::

GitHub opens with the App settings filled in. Confirm the name and select **Create GitHub App**.

## Copy the environment variables

GitHub sends you back to your site. The result page shows a block of environment variables. Select **Copy**.

::warning
The block holds the secrets of the App. Pluto does not store it. Copy it before you leave the page.
::

## Paste them in Vercel

In Vercel, open **Settings**, then **Environment Variables**. Paste the block into the first field: Vercel reads the lines and fills the rows. Save. Then redeploy, so that the site reads the new values.

::pluto-screenshot{name="deploy-vercel-env" alt="The Vercel environment variables page with the pasted values" hint="Vercel: Settings > Environment Variables, after the paste"}
::

## Install the App and sign in

On the result page, select the install link. Install the App on your repository only. Then open `/admin/login` and select **Sign in with GitHub**.

If you left the result page, open `/admin/login` again. The checklist shows an **Install the App** link.

::

Every user with push access to the repository can sign in and edit. After the redeploy, the setup routes answer 404, so nobody can create a second App on the live site.

## A save on the live site

A save is a commit on GitHub. The blog reads the posts from GitHub at run time, with a cache, so a post shows in seconds with no new build. The commit message ends with `[skip ci]`, so Vercel does not rebuild for each save.

A site that builds its pages from the content files must rebuild on each save. See [Commits and rebuilds](/docs/git-cms/reference#commits-and-rebuilds).

## If something goes wrong

- The result page or the settings page shows a problem: see [Troubleshooting](/docs/git-cms/troubleshooting).
- You prefer to create the App by hand: see [GitHub App](/docs/git-cms/github-app).
- You want the GitHub sign-in on your machine too: see [Test GitHub on your machine](/docs/git-cms/reference#test-github-on-your-machine).

## Deploy a Supabase project

A project with the Supabase backend needs these variables in Vercel before the first deploy:

| Variable | Value |
| --- | --- |
| `SUPABASE_URL` | The Supabase project URL |
| `SUPABASE_KEY` | The publishable key |
| `DATABASE_URL` | The Postgres connection string. The admin uses it to apply the migrations. Without it, the setup page asks for it. |

The first visit to `/admin` opens `/admin/setup`. See [Supabase](/docs/supabase). Optional variables, such as the mail key, go in the environment of the running server, not the build. See [Email](/docs/build/mail).
