On a live site, the posts stay in your GitHub repository. Editors sign in with GitHub, and each save is a commit on GitHub. You do not fill in any GitHub settings by hand: Pluto sends them to GitHub, and GitHub creates the App after you confirm.

You need:

- The project from the [Quickstart](/docs/start-here/quickstart), pushed to a GitHub repository.
- A host with a server runtime, such as [Vercel](https://vercel.com/) or [Netlify](https://www.netlify.com/). This page uses Vercel. For a static site with the admin on your computer, see [A static site on GitHub Pages](#a-static-site-on-github-pages).

In the admin on your computer, open **Settings**, then **Deploy**. The tab links to each host, and sets up GitHub Pages for you.

::pluto-screenshot{name="deploy-settings-tab" alt="The Deploy tab of the settings, with the hosts" hint="/admin/settings/deploy in local mode: the host cards and the GitHub Pages card"}
::

::steps{level="2"}

## Deploy the site

In **Settings → Deploy**, select **Deploy to Vercel**. Vercel opens the import page of your repository. Deploy. Vercel detects Nuxt. You set no environment variable now: the site builds and runs without the GitHub App.

::pluto-screenshot{name="deploy-vercel-import" alt="The Vercel page that imports a GitHub repository" hint="Vercel: Import Git Repository, with the Pluto project selected"}
::

## Create the GitHub App

Open `https://<your-site>/admin/login`. The page shows the checklist **Set up the GitHub sign-in**. Select **Create the GitHub App**.

::pluto-screenshot{name="deploy-github-checklist" alt="The sign-in page with the GitHub setup checklist" hint="/admin/login on the live site, with the Set up the GitHub sign-in checklist"}
::

GitHub opens with the App settings filled in. Confirm the name and select **Create GitHub App**.

## Copy the environment variables

GitHub sends you back to your site. The result page shows a block of environment variables. Select **Copy**.

::warning
The block holds the secrets of the App. Pluto does not store it. Copy it before you leave the page.
::

## Paste them in Vercel

In Vercel, open **Settings**, then **Environment Variables**. Paste the block into the first field: Vercel reads the lines and fills the rows. Save. Then redeploy, so that the site reads the new values.

::pluto-screenshot{name="deploy-vercel-env" alt="The Vercel environment variables page with the pasted values" hint="Vercel: Settings > Environment Variables, after the paste"}
::

## Install the App and sign in

On the result page, select the install link. Install the App on your repository only. Then open `/admin/login` and select **Sign in with GitHub**.

If you left the result page, open `/admin/login` again. The checklist shows an **Install the App** link.

::

Every user with push access to the repository can sign in and edit. After the redeploy, the setup routes answer 404, so nobody can create a second App on the live site.

## A save on the live site

A save is a commit on GitHub. The blog reads the posts from GitHub at run time, with a cache, so a post shows in seconds with no new build. The commit message ends with `[skip ci]`, so Vercel does not rebuild for each save.

A site that builds its pages from the content files must rebuild on each save. See [Commits and rebuilds](/docs/git-cms/reference#commits-and-rebuilds).

## Other hosts

### Netlify

In **Settings → Deploy**, select **Deploy to Netlify**, then pick your repository. Netlify detects Nuxt, and Pluto reads the repository from the Netlify build. Then do the steps above from [Create the GitHub App](#create-the-github-app): paste the variables in **Site configuration → Environment variables** and deploy again.

### A Node host

Any host that runs Node.js 22 or later works, for example a VPS, Render, Railway, or Fly.io.

1. Build: `npm run build`. The output is in `.output/`.
2. Start: `node .output/server/index.mjs`. Set `PORT` if the host asks for one.
3. Set `PLUTO_GITHUB_REPO` to `owner/name` before the build. Pluto finds the repository by itself on Vercel and Netlify only.
4. Do the steps above from [Create the GitHub App](#create-the-github-app). Set the variables in the environment of the running server, then restart it.

## A static site on GitHub Pages

The site can be plain files on [GitHub Pages](https://pages.github.com/), for free. There is no server, so the admin stays on your computer: you write in the admin, push, and a GitHub Action builds the site again. The build reads the Markdown in the repository, so it needs no token and no secret.

1. In the admin on your computer, open **Settings → Deploy**. In the **GitHub Pages** card, select **Add the workflow**, then confirm. Pluto writes `.github/workflows/pluto-pages.yml` and commits it to your local repository. It changes nothing on GitHub.
2. Select **Pages settings on GitHub**. Under **Build and deployment**, set **Source** to **GitHub Actions**. You do this one time.
3. Push. Use the **Push** button of the card, the Git badge in the admin bar, or `git push`. The first build takes a few minutes.
4. Select **Check again**. When the build is done, the card shows the address of the site, for example `https://<owner>.github.io/<repository>/`. If the build fails, select **Open the build log**.

You need Git only. Pluto reads the result of the last build from the GitHub API. For a private repository, it needs the GitHub App or a read token in `.env` to read the result. See [Reference](/docs/git-cms/reference).

::pluto-screenshot{name="deploy-github-pages" alt="The GitHub Pages card of the Deploy tab, after the setup" hint="The GitHub Pages card with the four steps green, the Online badge, and the Open the site button"}
::

The workflow builds with `nuxt build --preset github_pages`. A project site lives under `/<repository>/`: the workflow gives that path to the build in `PLUTO_BASE_URL`, and Pluto puts it before the links and the images of the site and of each post. Drafts are not in the output.

An admin on a Node host can publish to the same static site: set `plutoGithub.commit.skipDeploy` to `false`, so that each save of published content starts the Action. See [Commits and rebuilds](/docs/git-cms/reference#commits-and-rebuilds).

### Stop using GitHub Pages

In the admin on your computer, open **Settings → Deploy**. In the **GitHub Pages** card, select **Remove GitHub Pages**, then confirm. Pluto deletes the workflow and commits the change. It changes nothing on GitHub.

1. Push, so that GitHub stops building the site.
2. The last site stays online. To take it offline, open the Pages settings of the repository and select **Unpublish site**.

### Cloudflare Pages

Cloudflare Pages can build the same static site. Connect the repository in Cloudflare, and use the build command `npx nuxt generate` and the output directory `.output/public`.

## Use your own domain

Open **Settings → Deploy**, then go to **Domain**.

### On Vercel or Netlify

The host serves the domain and gets the HTTPS certificate. Add the domain in the domain settings of the host. Then add the DNS records that the host shows at your domain registrar.

The live admin knows its host. It shows the current address of the site and a link to the domain settings of that site. The admin on your computer shows a link for each host.

### On GitHub Pages

The domain is in the Pages settings of the repository. The **GitHub Pages** card of **Domain** shows the steps, the DNS records for your domain, and a check of the DNS.

::pluto-screenshot{name="deploy-domain" alt="The Domain section of the Deploy tab, with the steps for GitHub Pages" hint="/admin/settings/deploy: the domain field, the DNS records, and a green DNS check"}
::

1. Set up GitHub Pages first. See [A static site on GitHub Pages](#a-static-site-on-github-pages).
2. Type your domain in the **Your domain** field, for example `blog.example.com`.
3. Select **Pages settings on GitHub**. Type the domain under **Custom domain**, and save.
4. Add the DNS records that the card shows at your domain registrar:
   - For a subdomain, such as `blog.example.com`: a `CNAME` record to `<owner>.github.io`.
   - For an apex domain, such as `example.com`: the four `A` records and the four `AAAA` records of GitHub Pages.
5. Select **Check the DNS**. Pluto looks up the domain and tells you if it points to GitHub Pages. New records can take a few hours to work.
6. Build the site again: the site moves from `/<repository>/` to the root of the new domain. Select **Open the workflow**, then **Run workflow** on GitHub. Or push a commit.
7. When GitHub has the HTTPS certificate, turn on **Enforce HTTPS** in the Pages settings. This can take up to an hour.

::note
Pluto does not write a `CNAME` file. GitHub ignores that file when a GitHub Action builds the site.
::

To stop using the domain, clear it in the Pages settings. Then build the site again. The site goes back to `https://<owner>.github.io/<repository>/`.

## Deploy a template in one click

The README of each template has **Deploy with Vercel** and **Deploy to Netlify** buttons. A button copies the template to a new repository in your GitHub account and deploys it. For the blog and the admin templates, the copy uses the Git CMS: open `/admin/login` on the new site and create the GitHub App, as in the steps above. For the shop template, the host asks for the Supabase values first.

## If something goes wrong

- The result page or the settings page shows a problem: see [Troubleshooting](/docs/git-cms/troubleshooting).
- You prefer to create the App by hand: see [GitHub App](/docs/git-cms/github-app).
- You want the GitHub sign-in on your machine too: see [Test GitHub on your machine](/docs/git-cms/reference#test-github-on-your-machine).

## Deploy a Supabase project

A project with the Supabase backend needs these variables in Vercel before the first deploy:

| Variable | Value |
| --- | --- |
| `SUPABASE_URL` | The Supabase project URL |
| `SUPABASE_KEY` | The publishable key |
| `DATABASE_URL` | The Postgres connection string. The admin uses it to apply the migrations. Without it, the setup page asks for it. |

The first visit to `/admin` opens `/admin/setup`. See [Supabase](/docs/supabase). Optional variables, such as the mail key, go in the environment of the running server, not the build. See [Email](/docs/build/mail).
