The public site reads published posts through the [Public API](/docs/build/public-api) of core. The composables and the component are for a Nuxt site. A site in any other framework or stack calls the routes. See [Use Pluto headless](/docs/build/use-pluto-headless).

A public read is anonymous. The answer is the same for every visitor. A visitor never sees a draft. An exception: with `?drafts=1`, an editor of the type also gets a draft on the item route. The answer then has `meta.draft: true` and `Cache-Control: private, no-store`. A scheduled post shows from its planned time. The response never sets a cookie.

## Routes

The post type of the CMS is public: `api: { public: true }`.

- `GET /api/pluto/v1/content/post` returns the published posts: `{ data, meta: { total, limit, offset } }`. A list item has no body. It has `excerpt`: the `excerpt` field when it has text, else a plain text version of the body (200 characters).
- `GET /api/pluto/v1/content/post/<slug>` returns one published post: `{ data }`. It has the Markdown body and `html`, the body rendered and sanitized.
- The list takes `limit` (1 to 100, default 20), `offset`, `search`, `sort` (for example `-publishedAt`), and `filter[<field>]`.
- A missing file, or a draft for a visitor, gives 404. A nested type works too: the id can hold slashes.
- A success answer has `Cache-Control: public, s-maxage=60, stale-while-revalidate=300`. Set the time with `runtimeConfig.plutoApi.maxAge`. An error answer has no public cache header.

Your own content types work the same way when they set `api: { public: true }`. See [Public API](/docs/build/public-api).

## Composables

`usePosts` and `usePost` wrap `useFetch`. They run on the server, so the page HTML holds the data.

```vue [app/pages/index.vue]
<script setup lang="ts">
const { posts } = await usePosts({ limit: 10 })
</script>

<template>
  <article v-for="post in posts" :key="post.id">
    <h2>{{ post.title }}</h2>
    <p>{{ post.excerpt }}</p>
  </article>
</template>
```

```vue [app/pages/posts/[slug].vue]
<script setup lang="ts">
const route = useRoute()
const { post } = await usePost(() => String(route.params.slug))
</script>

<template>
  <PlutoHtml :html="post?.html ?? ''" />
</template>
```

- `usePosts({ limit, search, sort, filter, page })` gives `posts`, newest first, with `total`, `page` and `pages`. The page comes from `?page=` of the URL.
- `usePost(slug)` gives `post`, with `html`. A missing slug, or a draft for a visitor, shows the error page with a 404. When the admin bar shows, the page shows the draft. Set `drafts: false` to stop this. It also sets the SEO tags and **Edit Post** in the admin bar.

See [Public API](/docs/build/public-api#in-a-nuxt-site) for the options, your own content types, and the low-level composables.

## `PlutoHtml`

`PlutoHtml` is a core component. It shows the sanitized `html` of a public item, from the Git CMS or from any other backend (for example `@plutocms/supabase-blog`), so a page works with both.

| Prop | Default | Meaning |
| --- | --- | --- |
| `html` | none | The `html` of a public item |
| `tag` | `article` | The wrapper element |
| `class` | none | Extra classes for the wrapper |

The component sets the HTML as `innerHTML`. It never parses Markdown on the client. Pass only the `html` of a public item to it.

`PlutoMarkdown` is the older name, for the Git CMS only. It renders `PlutoHtml`.

## How the Markdown renders

Pluto renders Markdown with `marked` and GFM. Raw HTML in the Markdown never reaches the output. Then a sanitizer runs on the result.

The rendered HTML is cached by blob id. A blob id never changes, so the entry never goes stale.

See [Security](/docs/git-cms/security) for the sanitizer rules.

## Offset your header for the admin bar

On a public page, the admin bar shows for staff only. It is fixed at the top of the page. Core sets the token `--pluto-admin-bar-height` (`2.5rem`) on `:root`. While the bar shows, `PlutoRoot` sets `data-pluto-admin-bar` on `<html>`. When the server renders the bar (see [The bar in the first paint](/docs/extend/admin-shell#the-bar-in-the-first-paint)), the attribute is in the server HTML too, so the header does not move.

`PlutoRoot` moves the page down by the height of the bar. A Nuxt UI `UHeader` needs nothing: Pluto gives it the class `pluto-header-offset`. While the bar shows, the header sticks under the bar and keeps its height (`--ui-header-height` of your site, `4rem` by default), and the page aside and the table of contents stick under both. A header that is not a `UHeader` gets the same offset with the class `pluto-header-offset`, or with your own CSS. To write the offset yourself, use the token and the attribute:

```css
:root[data-pluto-admin-bar] .site-header {
  top: var(--pluto-admin-bar-height);
}
```

In script, `usePlutoAdminBar().visible` tells if the bar shows. See [Admin shell](/docs/extend/admin-shell).

## Show "Edit Post" in the admin bar

The post type shows **New Post** in the admin bar. To show **Edit Post** on a post page, tell core which post the page shows:

```ts [app/pages/posts/[slug].vue]
const route = useRoute()
usePlutoEditLink('post', () => String(route.params.slug))
```

The function also returns the edit link for staff, and `null` for a visitor. See [New and Edit buttons](/docs/extend/admin-shell#new-and-edit-buttons).
