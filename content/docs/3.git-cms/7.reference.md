## Options

Set the options under `plutoGithub` in `nuxt.config.ts`. Most sites set none. See [Defaults](#defaults).

| Option | Default | Rule |
| --- | --- | --- |
| `enabled` | `'auto'` | `'auto'`, `true` or `false`. `'auto'` turns the CMS on unless a backend layer is present. See [Git CMS](/docs/git-cms#on-unless-a-backend-layer-is-present). |
| `storage` | `'fs'` in development, `'github'` in production | `'github'` or `'fs'`. `'fs'` is valid in development only. |
| `github.repo` | Found by Pluto. See [Defaults](#defaults). | `owner/name`. Required when storage is `github`. |
| `github.branch` | `'main'` | The branch to read and commit to. |
| `github.appSlug` | The env var `NUXT_PLUTO_GITHUB_APP_SLUG` or `PLUTO_GITHUB_APP_SLUG`, else `''` | The slug of the GitHub App. |
| `github.apiUrl` | `'https://api.github.com'` | The API base URL. |
| `dir` | `'content'` | A relative path. No `..`, no leading `/`, no drive letter. The module changes `\` to `/` and removes a trailing `/`. |
| `commit.local` | `true` | In development (`storage: 'fs'`), commits each save to the local Git repository of the project. Set it to `false` to only write the files. |
| `commit.skipDeploy` | `false` | `false`: only a draft save gets a `[skip ci]` marker, so each save of published content starts a build. `true` adds the marker to every commit message, so no save starts a build. See [Commits and rebuilds](#commits-and-rebuilds). |
| `cache.headTtl` | `60` | Seconds. Zero or more. |
| `cache.storage` | `'cache'` | The Nitro storage mount for the cache. |
| `postType` | `true` | Registers the fixed post content type and the term types `tag` and `category`, on the server and on the client. With `false`, the admin does not show Posts and does not register the post capabilities or the term types. A layer that brings its own types sets it to `false`. |

A bad option turns the CMS off and logs an error. The module does not throw.

The cache time of the public answers is `runtimeConfig.plutoApi.maxAge` of core. See [Public API](/docs/build/public-api#cache-and-cors).

## Defaults

An explicit option always wins over a default.

**Storage.** In development, the storage is `fs`. In production, it is `github`. The env var `PLUTO_GITHUB_STORAGE=github` makes a development server use GitHub.

**Repository.** When `github.repo` is not set, Pluto looks in this order and uses the first match:

1. The env var `NUXT_PLUTO_GITHUB_REPO`, then `PLUTO_GITHUB_REPO`.
2. The Vercel variables `VERCEL_GIT_REPO_OWNER` and `VERCEL_GIT_REPO_SLUG`.
3. In development only, the `origin` remote of the local git repository. Pluto reads `.git/config` and accepts the https and ssh URLs of `github.com`. It runs no shell command.

**Missing repository.** In production, with the storage `github` and no repository, the module logs one error and the CMS stays off. The build does not fail. Set `PLUTO_GITHUB_REPO`, or set `plutoGithub.github.repo`. A `nuxt prepare` run stays quiet.

A site on Vercel, or a site that runs the dev server in its own git clone, needs no `plutoGithub` option. A build on another host sets `PLUTO_GITHUB_REPO`.

## Environment variables

The secrets are run-time variables. The module does not check them at build time. Set the secrets as `NUXT_PLUTO_GITHUB_<NAME>`.

The setup wizard writes these values for you. See [Deploy](/docs/start-here/deploy). To fill them by hand, see [GitHub App](/docs/git-cms/github-app).

| Variable | Required | Value |
| --- | --- | --- |
| `PLUTO_GITHUB_REPO` | No | `owner/name` of the repository. Pluto finds it in most cases. See [Defaults](#defaults). |
| `PLUTO_GITHUB_APP_SLUG` | No | The URL name of the GitHub App (`github.com/apps/<slug>`). |
| `PLUTO_GITHUB_STORAGE` | No | Set to `github` to test against GitHub in development. |
| `NUXT_PLUTO_GITHUB_SESSION_PASSWORD` | Yes | 32 characters or more, random. |
| `NUXT_PLUTO_GITHUB_APP_ID` | Yes | The App ID. |
| `NUXT_PLUTO_GITHUB_CLIENT_ID` | Yes | The Client ID. |
| `NUXT_PLUTO_GITHUB_CLIENT_SECRET` | Yes | The client secret. |
| `NUXT_PLUTO_GITHUB_PRIVATE_KEY` | Yes | The private key of the App. See [Private key formats](#private-key-formats). |
| `NUXT_PLUTO_GITHUB_READ_TOKEN` | No | A read-only token. It replaces the installation token for anonymous reads. |
| `NUXT_PLUTO_GITHUB_ALLOWED_USERS` | No | GitHub logins, comma-separated, without case. When set, only these users can sign in, even with push access. |

The module puts a non-secret copy of `enabled`, `repo`, `branch`, `appSlug`, `storage`, `dir`, `postType`, and `skipDeploy` in `runtimeConfig.public.plutoGithub`.

### Old names

Before version 0.28, the variables had `CMS` names, such as `NUXT_PLUTO_CMS_GITHUB_APP_ID` and `PLUTO_CMS_REPO`. Pluto 0.29 does not read them. Rename them in your host and in `.env`: `NUXT_PLUTO_CMS_GITHUB_<NAME>` and `NUXT_PLUTO_CMS_<NAME>` become `NUXT_PLUTO_GITHUB_<NAME>`, and `PLUTO_CMS_<NAME>` becomes `PLUTO_GITHUB_<NAME>`.

## Private key formats

The variable `NUXT_PLUTO_GITHUB_PRIVATE_KEY` accepts three formats:

- A PEM with real line breaks.
- A PEM on one line, with a literal `\n` for each line break.
- The base64 of the PEM, on one line. The value has no `-----BEGIN` text. Pluto decodes it and uses the result when it holds a PEM.

The setup wizard writes the base64 format. One line is easy to paste in a host dashboard.

To make the base64 value of a `.pem` file yourself, run `base64 -w0 key.pem`.

## A minimal config

With the defaults, a site sets only the options that differ:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@plutocms/core'],
  plutoGithub: {
    github: { branch: 'content' }, // only when the branch is not main
    dir: 'docs-content' // only when the folder is not content
  }
})
```

## Develop with local Git

In development, the CMS uses `storage: 'fs'` by default. The dev server reads and writes the local `content/` folder, and commits each save to the local Git repository of your project. It never pushes: you push when you are ready.

- One save is one commit, with a message such as `content(post): create "hello"`. The commit holds only the files of that save. Changes that you staged in other files stay staged.
- The commit uses your Git name and email, and runs the hooks of your repository.
- `create-pluto` makes the new project a Git repository with a first commit, so this works on the first save.
- Without a Git repository, or without Git, Pluto only writes the files and logs a warning. Run `git init` to commit each save.
- If a commit fails (for example, a hook stops it), the save is still on disk. The server log says why.
- A local commit has no `[skip ci]` marker, so your push deploys as usual.
- To only write the files, set `commit.local: false`.

Local Git publishing works in development only. `storage: 'fs'` is an error in a build. On a deployed site, the admin saves only when a GitHub App is connected. See [Deploy](/docs/start-here/deploy).

Open `http://localhost:3000/admin`. On your machine, you are signed in as a fixed local user with all capabilities. No GitHub step is needed.

The `fs` store uses the project directory as the root, so a post is at `<project>/content/posts/<slug>.md`.

::note
The dev local user works only for a request from your machine. A request with `x-forwarded-for` or `forwarded` is not local. A request whose `Host` is not `localhost`, `127.0.0.1`, or `[::1]` is not local either. A tunnel or a DNS-rebinding page gets no access.
::

### Test GitHub on your machine

You need no GitHub App to edit on your machine. Do these steps to test the GitHub sign-in locally, or to edit the real repository:

1. Run the dev server. Open **Admin → Settings → GitHub**.
2. Select **Create the GitHub App**. Confirm on GitHub.
3. Pluto saves the values in the `.env` file of the project. The result page shows them too, so you can copy them to a host later. Restart the dev server so that it reads them.
4. Install the App on the content repository. The settings page links to the install page.

Set `PLUTO_GITHUB_STORAGE=github` in `.env` to make the dev server use the GitHub repository. See [Environment variables](#environment-variables).

## Deploy

Deploy to a host with a server runtime, such as Vercel, Netlify, or Node. The site then reads the posts at run time. A static site on GitHub Pages also works: each push builds the site again, and the admin stays on your computer. See [Deploy](/docs/start-here/deploy).

## Commits

Commit messages have this form. `<type>` is the name of the content type. For the built-in type, it is `post`.

- `content(<type>): create "slug"`
- `content(<type>): update "slug"`
- `content(<type>): publish "slug"` and `unpublish`
- `content(<type>): rename "a" -> "b"`
- `content(<type>): delete "slug"`

A save that changes nothing makes no commit.

The rename or the delete of a tag or a category also rewrites the posts that use it, in the same commit. The message ends with the count, for example `content(tag): rename "a" -> "b" (3 references)`. See [Tags and categories](/docs/build/tags-and-categories#git-cms).

With `commit.skipDeploy` off (the default), only a save that changes no published content gets a `[skip ci]` marker: a draft that stays a draft. So a draft save starts no build. A publish, an unpublish, and each change of a published item start a build. A content type with no status always starts a build.

A media upload, change, or delete always gets the marker. The site serves a new file at run time, and the next save of published content puts it in the build.

With `commit.skipDeploy` on, the marker ends every message. A host that honors the marker does not rebuild on each save. Not every host reads this marker. Test it on your host. With `skipDeploy` on, the edit form shows no [build status](/docs/git-cms/editing#build-status).

## Commits and rebuilds

On Vercel, Pluto finds the repository from the Vercel variables, so you need not set `plutoGithub.github.repo`.

By default, the Git CMS is hybrid:

- **A save shows at once.** The server reads the content from GitHub at run time, with the [cache](#cache).
- **A save of published content starts a build.** The build puts a copy of the Markdown files of the content directory in the server bundle.
- **The site stays up when GitHub does not answer.** When a read from GitHub fails (an outage, a rate limit, a bad App key), the public pages show the copy of the last build. A signed-in editor gets the error: the admin does not edit old content.
- **Before the GitHub App exists**, on a first deploy, the public pages show the copy of the build.

A static site, such as a [GitHub Pages](/docs/start-here/deploy) site, changes only with a build, so it needs this default too.

To stop the build after each save, set `commit.skipDeploy` to `true`. A save still shows at once, but the copy of the build and a static site get old.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  plutoGithub: {
    commit: { skipDeploy: true }
  }
})
```

::note
Not every host honors `[skip ci]`. Test it on your project, and check the documentation of your host. Vercel has an "Ignored Build Step" setting that lets a project skip a build by rule.
::

## Cache

The store keeps these in a cache:

- The head of the branch, for `cache.headTtl` seconds.
- The directory index, by `<dir>@<headOid>`.
- The tree index of a nested type, by head.
- The parsed files, by blob id.
- The rendered HTML and the excerpts, by blob id.

A blob id never changes, so a blob entry never goes stale. The default backend is a `Map`. With `cache.storage`, the cache uses a Nitro storage mount.

## GitHub Enterprise Server

Set `plutoGithub.github.apiUrl` to `https://<host>/api/v3`. The OAuth pages use `https://<host>`. Any other API URL uses `https://github.com`.

## Rate limits

When GitHub rate limits a call, the CMS answers 503 with a `Retry-After` header.
