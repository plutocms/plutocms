Editors write content in the Pluto admin at `/admin`. The CMS registers the `post` content type, so the generic list and form pages work. See [Lists and forms](/docs/extend/forms).

::pluto-screenshot{name="git-cms-editor" alt="The post editor of the Git CMS" hint="A post in the editor, with the preview and the build status"}
::

To use your own content types, set `plutoGithub.postType: false`. The server then registers no post type, and the admin shows no Posts entry. A layer, such as the [docs layer](/docs/layers/docs), registers its own types.

## Drafts and publishing

A draft is a post with `status: draft` in its frontmatter. The public routes never show a draft.

The adapter sets the timestamps. A payload cannot set them. It sets `publishedAt` on the first publish only. Without a `timestamps` setting, the keys are `createdAt` and `updatedAt`.

The post type can be scheduled. **Schedule** keeps the post with `status: scheduled` and the planned time in `publishedAt`. The commit has `[skip ci]`, so it starts no deploy. At the time, a server read shows the post. The scheduled task `pluto:publish:scheduled` then commits `status: published` in one commit, `content(post): publish N scheduled`. This commit starts a deploy. Every editor of the Git CMS can publish, so the post type has no review step. See [Scheduled publish](/docs/extend/forms#scheduled-publish).

::warning
In a public repository, anyone can read a draft on GitHub. The dashboard shows a warning for a public repository. Use a private repository if your drafts must stay private.
::

### Scheduled posts on GitHub Pages

A static site has no server and no scheduled task. The GitHub Pages workflow that Pluto writes (`.github/workflows/pluto-pages.yml`) also runs every hour:

1. A short job looks at every Markdown file in the content folder. A post with `status: scheduled` and a `publishedAt` that has come gets `status: published`. Only that line changes.
2. The job commits the change (`content: publish N scheduled`) and pushes it.
3. The build and the deploy run only when the job published a post.

GitHub can start a scheduled run some minutes late. To change the rhythm, edit the `cron` line of the workflow. An older workflow does not have the job: the Deploy page shows it as old. Add the new workflow again from the Deploy page.

::note
A branch protection rule that refuses the push of `github-actions[bot]` stops the job.
::

## Who can do what

- An anonymous caller sees published items only.
- A signed-in caller sees drafts only with the read capability of the type (`posts:read_drafts` for posts). The capability `*` counts as every capability.
- Every write needs a signed-in user (401). It needs the write or delete capability (403). A change of the published state needs the publish capability.
- A user with push access gets the capabilities of every registered content type.

## The Markdown editor

The body of a post uses a Markdown editor. The widget is `PlutoFieldMarkdown`, a `richtext` field widget. It uses `UEditor` from Nuxt UI, which is built on Tiptap. The model value is a Markdown string.

The toolbar has:

- Undo and redo.
- Headings 1 to 4.
- Bulleted and numbered lists.
- Quote and code block.
- Bold, italic, strikethrough, and inline code.
- A link button with a popover for the URL.

The image extension is on. The image button shows when the app has a media library. The mention extension is off.

The widget loads on demand, so Tiptap loads on the edit page only. The post type shows the widget in the [post editor](#the-post-editor).

### Visual and Source modes

The widget has a **Visual** and a **Source** button. Source is `PlutoMarkdownSource`: a monospace text area that grows with the text. It never parses or rewrites the text.

A `richtext` field can set `editor` to choose the first mode:

| `editor` | First mode |
| --- | --- |
| `'auto'` (default) | Source when the text has syntax that the visual editor cannot keep. Visual otherwise. |
| `'visual'` | Visual. |
| `'source'` | Source. |

`findUnsafeMarkdown(text)` lists that syntax. It gives one issue `{ kind, line }` for each kind: `mdc-block`, `mdc-inline`, `attributes`, `html`, `table`, `task-list`, `footnote`, and `fence-meta` (a code fence with more than a language). Text in a code fence or in inline code is ignored.

While the text has such syntax, the **Visual** button is off and a tooltip says why. It turns on again when the author removes the syntax in Source. An explicit `editor: 'visual'` still opens Visual.

A layer can use `PlutoMarkdownSource` to build its own field widget. It has the props `modelValue`, `disabled`, `placeholder`, `rows` (default 18), `maxRows`, `ariaLabel`, and `fill` (fill the height of the parent, and scroll the text inside). It has a `toolbar` slot with the slot props `insert` and `focus`. The component exposes `insert(text, { block })`, `focus()`, and `goToLine(line)`.

## The post editor

The `post` type edits its body in the post editor, like the page editor of the [docs layer](/docs/layers/docs). The editor fills the page between two panels:

- The left panel shows the outline: the headings of the post. Click a heading to go to it in the editor and in the preview.
- In the center, the compose panel is next to a live preview of the site. Drag the line between them to change their sizes. A **Preview** badge marks the preview. It fades out while the pointer is on the preview.
- The footer of the compose panel has the **Visual** and **Markdown** switch. **Visual** mode shows the Markdown editor above. **Markdown** mode shows the Markdown source in a code editor with syntax colors and a format toolbar (`PlutoMarkdownCodeEditor`).
- The right panel has the **Post** tab with the other fields: the title, the slug, the excerpt, and the cover image.

The editor keeps the last mode in a cookie. While the text has syntax that the visual editor cannot keep, the **Visual** button is off.

The post type sets it up:

```ts
fields: [
  // ...
  { name: 'content', type: 'richtext', widget: 'post-canvas' },
],
form: {
  layout: 'canvas',
  canvasField: 'content',
  leftPanel: { label: 'pluto.post.outline' },
},
```

The editor is in core, so any content type with a Markdown `richtext` body can use it. The [Blog layer](/docs/layers/blog) uses it too. In Visual mode it shows the `richtext` widget of the app with the `canvas` prop. A `richtext` widget of a layer must accept `canvas`: no label, and a column that fills the canvas.

### The preview

The preview is a frame of the page `/_pluto/post-preview` of your site, so the post shows with the CSS of the site. The page has no admin bar, and search engines do not index it. Links in the preview do not open.

The page renders the Markdown with the same code as the public API. It shows the default component `PlutoPostPreview`: the title, the date, the excerpt, and the body. To use the layout of your post page, add `app/components/PlutoPostPreview.vue` with the same props.

The `item` prop has the shape of the [Public API](/docs/build/public-api) item: `html` is the body, the dates are `createdAt`, `updatedAt`, and `publishedAt` for every backend, and a media field holds the file record, not its id. So the component of your post page can render it as it is:

```vue [app/components/PlutoPostPreview.vue]
<script setup lang="ts">
defineProps<{
  contentType: string
  item: PlutoPreviewItem<Post>
}>()
</script>

<template>
  <PostArticle :post="item" />
</template>
```

`Post` is the type of your post, the same one that your post page gives to `usePlutoPublicItem`.

Put `data-pluto-post-body` on the element that holds the body. The outline finds the headings in it to scroll the preview. The blog templates have this component. When you change your post page, change the preview too.

### Limits of the editor

::warning
The visual editor knows CommonMark and strikethrough. It has no node for MDC, a GFM table, a task list, or raw HTML. Use Source mode to edit a post that has them.
::

- The public page still renders tables and task lists from the stored Markdown.
- The visual editor can write the Markdown with other marks than the author used. For example, it can use `-` for a bullet. The text means the same.

## Build status

A save is a commit. When the commit starts a deploy, the site changes only after the build. The edit form shows the build of the last commit next to the **Save** button:

- **Publishing…** with a spinner while the build runs.
- **Live** with a check mark when the build passed.
- **Build failed** when a check or a deployment failed.

The **Info** button opens the details: the commit, and each check run, commit status, and deployment, with a link to its run or build page. The status shows only with GitHub storage when `commit.skipDeploy` is off (the default). When the host reports nothing for the commit, nothing shows.

A draft save starts no build, so the status shows the build of the last save that changed published content. On a draft that was never published, the status does not show.

The form asks again every 5 seconds while the build runs. It stops when the build ends, after 15 minutes, and while the browser tab is hidden. The route is `GET /api/_pluto/github/build-status`. It reads the check runs, the commit statuses, and the deployments of the head commit with the token of the user.

The GitHub App needs read access to **Checks**, **Commit statuses**, and **Deployments**. Without it, the details say so, and an App without any of them shows no status. See [Add the build status permissions](/docs/git-cms/github-app#add-the-build-status-permissions).

A content type that the site reads at run time sets `liveOnSave`, for example the posts, and the pages of the [docs layer](/docs/layers/docs) in hybrid mode. The form then shows **Live** right after the save, with a small spinner by the **Info** button while the static build runs. If that build fails, the site still serves the change at run time.

## History

Each save is a commit, so every post keeps its saved versions. The **History** button (a clock icon) next to **Save** opens them:

- The list shows each version, newest first: what it did (created, saved, published, unpublished, renamed), who saved it, and when. A commit that you pushed yourself shows its message.
- Select a version to see what a restore changes in the form: the old and the new value of a short field, and the changed lines of the body.
- **Restore this version** puts the fields of that version in the form. The slug and the status stay. Check the result, then save. The restore is a new version, so you can undo it the same way.

Only an editor of the type sees History. On a deployed site, the versions come from GitHub. On your machine, they come from the local Git repository of the project. The history of an item starts at its last rename.

## The trash

**Move to trash** moves a post, a tag, a category, or an author to the trash. The file moves to `content/.trash/<type>/` in one commit, and the site does not show it. The links from other posts stay.

The **Trash** tab of the list shows the items in the trash. **Restore** moves the file back. **Delete forever** deletes the file, and removes the links to it from the other posts, in one commit.

An item stays in the trash for 30 days. Then Pluto deletes it forever. A daily task does this on a server host. To commit, the task uses the GitHub App: it needs `NUXT_PLUTO_GITHUB_APP_ID` and `NUXT_PLUTO_GITHUB_PRIVATE_KEY`. Opening the Trash tab also deletes the old items. See [The trash](/docs/extend/forms#the-trash).

## Unsaved changes and backups

The form keeps a backup of your unsaved changes in the browser. A crash, a closed tab, or a failed save does not lose your work. The backup is not a save: it makes no commit, no build, and no new version in History. **Save** and **Publish** stay the only writes.

- The form writes the backup about 1 second after you stop typing, and at least every 5 seconds while you type. It also writes when you hide or close the tab.
- When you open the item again, the form compares the backup with the saved item. If they differ, a yellow alert shows above the fields: "Unsaved changes found. Changes from {time} were not saved."
- **Restore** puts the backed-up values in the form. Check them, then save. A field that only the saved item changed keeps its saved value.
- **Discard** deletes the backup.
- **Show changes** opens a panel with the saved value and the backup value of each changed field.
- If the item was saved again after the backup, and the same field changed in both places, the alert names the field. Restore then takes the backup value.

While the alert is open, the form does not write new backups. A click on **Save** (or Ctrl+S) opens the dialog "Discard the unsaved changes?". Choose **Cancel** to do nothing, **Restore** to restore without a save, or **Save and discard** to save the form as it is. The backup is then deleted.

The form deletes the backup after a save, after a delete, and when you choose **Leave without saving**. A failed save keeps it. A backup also expires after 14 days.

Each backup is for one user and one item. A new item has its own backup. A user keeps at most 20 backups. A backup that is larger than 1,000,000 characters is not kept.

If two tabs edit the same item, the last write wins. The form shows a warning in the other tab. There is no lock.

::warning
A backup is plain text in the storage of the browser. On a shared computer, sign out when you finish. Signing out deletes your backups in that browser. A session that expires keeps them. To keep the text of a content type out of the browser, set [`form.backup`](/docs/extend/forms#form-options) to `false`.
::

The backup works the same on every backend. The Git CMS keeps no copy on a server, so you cannot restore on another device. For that, see the [Supabase backups](/docs/supabase/content-adapter#backups).

A widget that holds text outside its value, for example an editor with a delay, can register an `onFlush` callback. See [Add a field widget](/docs/extend/add-a-field-widget#write-pending-edits-before-a-save).

## Conflicts

Every item has a `_version` token. It is the blob id of the file.

- An update with a stale `_version` gives 409. The form keeps your changes in the backup and shows the alert "Someone saved this item after you opened it. Your changes are safe." The button **Load the latest and keep my changes** loads the newest version and puts your changes on top of it. The form lists the fields that changed in both places. For those fields, your value wins. Check the form, then save.
- A create or a rename to a taken slug gives 409.
- A rename is one commit. It adds the new path and deletes the old one. For a nested type, a new path in the slug field moves the file the same way. See [Nested content types](/docs/git-cms#nested-content-types).
- An update whose new file text equals the stored text makes no commit. The call returns the stored item with the same `_version`. A hand-written file with a different YAML layout is not equal, so the first real save rewrites it.
- A commit uses a fresh head as `expectedHeadOid`. When the head is stale, the adapter retries up to 2 times. It retries only if the target file did not change. Otherwise it gives 409.

## Errors

Store errors map to HTTP errors:

| Store error | HTTP status |
| --- | --- |
| Conflict | 409 |
| Auth | 401 |
| Forbidden | 403 |
| Rate limit | 503 with `Retry-After` |
| Not found | 404 |
| GitHub failure | 502 |

## Admin pages and sign-in

The CMS adds no page, no route middleware, and no navbar. Core owns the `/admin` routes. The CMS is the reference auth driver. See [Admin shell](/docs/extend/admin-shell).

The client side of the auth driver:

- `user()` gives `id`, `name`, `username` (the GitHub login), and `avatarUrl`.
- `loggedIn()` reads the session, which loads in the browser only. It is `false` on the server and in the first client render. The navbar appears after hydration.
- `signOut()` posts to the logout route.

`usePlutoGithubSession()` gives `{ user, capabilities, repo, loggedIn, status, ready, refresh, logout }`.
