The layer registers a `PlutoContentAdapter` backed by Supabase and PostgREST. It plugs into the generic content routes of core, `/api/_pluto/content/[type]`. A content type that a layer declares maps onto a table, with no server code for each type. See [Content model](/docs/reference/content-model).

The Nitro plugin registers the adapter at startup with `registerContentAdapter`.

## What the adapter does not do

- **No schema generation.** A layer writes its SQL migration by hand. The adapter only maps a content type onto a table that already exists.
- **No relation resolution.** A `reference` field is stored and read back as a plain column value (an array column for `multiple`). Core expands it in the public API, and the widget reads its options from the `target` type or from `optionsUrl`.
- **No `describe()`.** The optional conformance warning is not part of this adapter.

## What the adapter does

The adapter has the id `supabase`. It implements `list`, `get`, `create`, `update`, `remove`, `authorize`, `countCreated`, `listRevisions`, `getRevision`, and `backups`.

- `list` counts the rows. It filters on the status column unless the caller asks for unpublished items. `search` is a case-insensitive match on the title column.
- `get` looks up the primary key first. If no row matches, and the type has a `slug`, it looks up the slug column.
- `list` takes `ids`: it returns only the rows with these primary keys (`.in()`). An empty list runs no query and returns no row.
- A filter on a `multiple` reference field uses `.contains` on the array column, so `filter[tags]=3` finds the rows whose `tag_ids` hold 3. Any other filter is an equality.
- `authorize` calls `requireCapability` for the capability that the generic route asks for.

## Field and column mapping

The adapter uses `fieldColumn`, `mapFieldsToColumns`, and `mapColumnsToFields` of core for every translation between a field payload and a database row. For `titleField`, `defaultSort.field`, and `slug.field`, it finds the field first and then calls `fieldColumn`. If the field does not exist, it guesses the column from the name and logs a warning.

## Timestamps

When a timestamp column resolves, `create` and `update` always overwrite it with the current time. A client never controls its own creation or update time. A timestamp column is off when `timestamps` is `false`, or when the key is `false`.

## Status

- A new row gets the default status only when the payload does not set the status column. An explicit status is respected.
- `update` sets `publishedAtColumn` to the current time the first time a row gets the `publishedValue`. It never overwrites a value that is already set on a later edit.
- A status other than `publishedValue` leaves `publishedAtColumn` alone. The adapter never clears it.

## Revisions

The adapter keeps the saved versions of every item, so the edit form shows [History](/docs/reference/content-model#revisions). The versions are in one table for every content type, `public.pluto_content_revisions` (migration 011 of the layer).

- After each create and update, the adapter writes the item, the action (created, saved, published, unpublished), and the name of the user.
- It keeps the newest 100 versions of each item. A delete removes the versions of the item.
- Row Level Security allows a user to read, add, and delete the versions of a type only with the write capability of that type. Nobody can change a version.
- An item saved before the migration has no version until its next save.
- If the table is not there yet, the save still works. The server logs a warning.

## Backups

The adapter keeps a server copy of the unsaved changes of each user, so an editor can restore them on another device. The edit form also keeps a [backup in the browser](/docs/git-cms/editing#unsaved-changes-and-backups). The adapter implements the optional `backups` of the [content model](/docs/reference/content-model#backups).

The copies are in one table for every content type, `public.pluto_content_backups` (migration 012 of the layer). A row holds one user, one type, and one item, and the record of the changes. A new item uses the item key `+new`.

- Row Level Security lets a user read, add, change, and delete only the rows of that user. An admin cannot read the rows of another user in the admin.
- The form sends the copy 10 seconds after the last change, and at least every 30 seconds. It sends it again when you hide the tab. No copy goes out while the browser is offline.
- A row expires after 14 days. Each user keeps at most 20 rows. A write removes the older rows.
- A save, a delete, **Discard**, and **Leave without saving** remove the row of the user.
- When you open an item, the form reads the browser backup and the server copy. The copy with the newer time wins. If both have the same time, the browser backup wins. If the server does not answer in 3 seconds, the form uses the browser backup. On another device, the server copy is the only one.
- When the copy comes from another device, the alert says "Changes from another device, from {time}, were not saved."
- If two devices edit the same item, the last write wins. The form shows a warning on the device that overwrote a recent copy. There is no lock.
- Signing out keeps the server copies. You get them back after the next sign-in. A form with `form.backup: false` writes no copy.

::warning
The server copy is text in your database. Only its owner reads it through the Data API. The `service_role` key, the database owner, and the database backups can read it too. Set [`form.backup`](/docs/extend/forms#form-options) to `false` on a type whose text must not be stored.
::

If migration 012 is not applied, the form keeps the browser backup only. A save still works. The server logs a warning. See [Migrations](/docs/supabase/migrations#migration-012).

Supabase returns no `_version` token. A concurrent save on Supabase overwrites the item and gives no 409. The backup still keeps the changes of the editor until the next save.

## Errors

The adapter logs the raw error first. Then it maps the Postgres `error.code` to an error that is safe to send:

| Postgres code | Meaning | HTTP status | Message |
| --- | --- | --- | --- |
| `23505` | Unique violation | 409 | A record with this value already exists. |
| `23503` | Foreign key violation | 400 | This references a record that does not exist. |
| Any other | | 500 | The raw `error.message` |

## Counting by date

The adapter implements `countCreated` with one exact-count HEAD query for each range. The dashboard activity chart uses it.

## Types are loose here, on purpose

The table name of a content type is a runtime string. The generated `Database` type cannot know a table that another repository declares. So this one file uses an untyped `SupabaseClient`. This is deliberate. Every other file in the layer keeps the typed client.

## Use it from a layer

A feature layer declares the content type and registers it. The adapter handles the storage. `supabase-shop` and `supabase-blog` work this way. See [Shop (Supabase)](/docs/layers/supabase-shop) and [Blog (Supabase)](/docs/layers/blog).
