Editors sign in with a GitHub App. The sign-in uses the user-to-server OAuth web flow. Only users with push access to the content repository can sign in. You need one GitHub App for each site.

::note
Use the admin to create the App: open `/admin/login` on the deployed site (or **Settings → GitHub** in development) and select **Create the GitHub App**. See [Quickstart](/github-cms/quickstart). The manual steps below also work. Use them when you cannot use the admin, for example when your organization does not let you create an App from a manifest.
::

## Create the App by hand

::steps{level="3"}

### Create the App on GitHub

Open **Settings, Developer settings, GitHub Apps, New GitHub App**. For an organization, open **Organization settings, GitHub Apps**.

Use these settings:

- **Homepage URL:** the URL of your site.
- **Callback URL:** `https://<your-site>/api/_pluto/auth/github/callback`. Add `http://localhost:3000/api/_pluto/auth/github/callback` too if you want to test sign-in locally. See [Callback URLs](/github-cms/troubleshooting#callback-urls).
- **Expire user authorization tokens:** on. The session refreshes tokens that expire.
- **Request user authorization (OAuth) during installation:** off.
- **Webhook, Active:** off.
- **Repository permissions:** **Contents** read and write, **Metadata** read-only. For the [build status](/github-cms/editing#build-status), also **Checks**, **Commit statuses**, and **Deployments** read-only. Nothing else.

### Collect the credentials

On the App page, note the **App ID** and the **Client ID**. Generate a **client secret** and a **private key** (a `.pem` file). The URL name of the App (`github.com/apps/<slug>`) is the **app slug**.

### Install the App

Install the App on the content repository only.

### Set the environment variables

Set `PLUTO_GITHUB_APP_SLUG` and the `NUXT_PLUTO_GITHUB_*` variables in `.env` for local use, and in your host for production. The [Reference](/github-cms/reference#environment-variables) lists every variable and the [private key formats](/github-cms/reference#private-key-formats).

### Deploy

Deploy to a host with a server runtime. If a check fails, see [Troubleshooting](/github-cms/troubleshooting).

::

## Add the build status permissions

The admin shows the [build status](/github-cms/editing#build-status) of a save. It needs read access to **Checks**, **Commit statuses**, and **Deployments**. An App that the admin creates asks for them. An App created before Pluto 0.26, or by hand without them, does not have them, and the build status does not show.

1. Open the App settings on GitHub, then **Permissions & events**.
2. Under **Repository permissions**, set **Checks**, **Commit statuses**, and **Deployments** to read-only. Save.
3. Open the installation of the App (**Install App**, then the gear icon), and accept the new permissions.

## The sign-in flow

1. `GET /api/_pluto/auth/github/login?redirect=/path`. The `redirect` must be a path on this site. Any other value becomes `/admin/home`. The route makes a `state` value and a PKCE verifier. It saves them in a separate sealed session (`pluto-github-oauth`) that lives 10 minutes. Then it answers 302 to GitHub.
2. `GET /api/_pluto/auth/github/callback`. The route reads and clears the saved session first, so `state` works once. It compares `state`. Then it trades the code for tokens, reads the user, and reads the repository with the **user** token.
3. `GET /api/_pluto/auth/session` answers `{ user, capabilities, repo: { name, private } }`, or `{ user: null }`. It never has a token.
4. `POST /api/_pluto/auth/logout` deletes the cookie and answers 204.

## Sign-in errors

The callback redirects to `/admin/login?error=<code>`. The codes are `state`, `not_installed`, `forbidden`, `denied`, and `github`. See [Troubleshooting](/github-cms/troubleshooting#sign-in-errors) for the cause and the fix of each code.

## Capabilities of a user

| GitHub permission | Capabilities |
| --- | --- |
| admin, maintain | `*` (all) |
| push | The read, write, publish, and delete capabilities of every registered content type. The post type is the fallback when no type is registered. |

For the built-in post type, these are `posts:read_drafts`, `posts:publish`, and `posts:delete`. A user with a lower permission cannot sign in.

In development with `storage: 'fs'`, a request from your machine gets a fixed local user with `*`. See [Reference](/github-cms/reference#develop-with-local-git).

GitHub still enforces the real permission on each commit, because the commit uses the user token.

## The sign-in page

The sign-in page is the core `/admin/login`. It has one **Sign in with GitHub** button. It is a full page load to the login route.

## Anonymous reads

An anonymous caller sees published posts only. The store reads with a server token:

1. `NUXT_PLUTO_GITHUB_READ_TOKEN`, a read-only token, when it is set.
2. Otherwise an installation token of the App, for this repository, with `contents: read`. The code signs an App JWT and caches the token in memory until 5 minutes before it ends.
3. With neither, an anonymous read answers 503 and logs the cause once. The server does not fail at boot.

A signed-in user reads and writes with their own token.
